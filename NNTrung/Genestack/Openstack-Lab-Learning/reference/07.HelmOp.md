# Helm chart, values và cơ chế post-render
## 1. Cấu trúc và phạm vi cấu hình của Helm chart
Ví dụ chart Nova chứa các mẫu để tạo Deployment, DaemonSet, Service, Secret… cùng cấu hình mặc định.

Chart cung cấp các template và giá trị mặc định. Cấu hình môi trường được bổ sung riêng cho các yếu tố sau:

- Hệ điều hành Talos và các đường dẫn có thể ghi.
- Vai trò, tên và nhãn của node.
- Loại storage và vị trí lưu dữ liệu.
- Kết nối OVS/OVN được dùng chung với Kube-OVN.
- Disk dành cho dữ liệu máy ảo.

## 2. Tổ chức tệp values theo môi trường
Thư mục overrides của cụm tham chiếu có cấu trúc sau:
```
~/osh-lab/overrides/
├── glance/
│   ├── 2026.1-ubuntu_noble.yaml
│   └── lab-worker-pvc.yaml
├── nova/
└── neutron/
```
- Trong đó:
  - `2026.1-ubuntu_noble.yaml`: cấu hình phù hợp bản OpenStack và image hệ điều hành đã chọn.
  - `lab-worker-pvc.yaml`: cấu hình riêng của cụm thử nghiệm.

Tên thư mục overrides là quy ước tổ chức, không phải yêu cầu của Helm. Helm đọc các tệp được chỉ định qua tham số `-f` hoặc `--values`.

Ví dụ:
```bash
helm template glance openstack-helm/glance \
  --version '2026.1.39+dd5656a9c' \
  --namespace openstack \
  --values ~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml \
  --values ~/osh-lab/overrides/glance/lab-worker-pvc.yaml \
  > /tmp/glance-rendered.yaml
```

Helm sẽ ghép:
```
Values mặc định của chart
          ↓
Cấu hình 2026.1-ubuntu_noble.yaml
          ↓
Cấu hình lab-worker-pvc.yaml
```

Khi các tệp có cùng khóa, giá trị của tệp xuất hiện sau được ưu tiên. Tham số `--set volume.size=10Gi` cung cấp giá trị trực tiếp trên dòng lệnh thay cho một tệp override.

helm template kết hợp chart và values để sinh manifests Kubernetes. Kết quả được lưu và kiểm tra bằng các công cụ tìm kiếm như rg, grep hoặc sed trước khi triển khai:

helm upgrade --install tạo hoặc cập nhật release bằng cấu hình được cung cấp:
```bash
helm upgrade --install glance openstack-helm/glance \
  --version '2026.1.39+dd5656a9c' \
  --namespace openstack \
  --values ~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml \
  --values ~/osh-lab/overrides/glance/lab-worker-pvc.yaml \
  --wait --timeout 15m
```

| Thành phần lệnh | Chức năng |
|---|---|
| `glance` đầu tiên | Tên lần triển khai, gọi là **release** |
| `openstack-helm/glance` | Chart dùng làm bộ cài |
| `-f ...` | Cấu hình được áp dụng |
| `upgrade --install` | Đã có release thì cập nhật; chưa có thì cài |
| `--wait` | Chờ các tài nguyên liên quan đạt trạng thái sẵn sàng |
| `--timeout 15m` | Giới hạn thời gian chờ |
| `--version '2026.1.39+dd5656a9c'`| Chọn phiên bản Helm chart Glance.|

Helm ghép lệnh trên như sau:
```
Values mặc định của chart phiên bản đã chọn
                  ↓ ghi đè
       2026.1-ubuntu_noble.yaml
                  ↓ ghi đè
          lab-worker-pvc.yaml
```


Quá trình thử và sửa diễn ra:
```
Viết values
    ↓
helm template → xem kết quả
    ↓
Phát hiện chưa đúng → sửa values/chart
    ↓
helm template → kiểm tra lại
    ↓
helm upgrade --install → áp dụng
    ↓
Kiểm tra Pod và chức năng thực tế
```

- **Chart**: bộ cài có sẵn.
- **Overrides**: tham số riêng của môi trường triển khai.
- **Render và triển khai**: sinh manifests để kiểm tra, sau đó tạo hoặc cập nhật release.

## 3. Tìm phiên bản chart và lưu vào biến
```bash
GLANCE_CHART_VERSION=$(helm search repo openstack-helm/glance --versions | awk 'NR==2 {print $2}')
printf 'Glance chart: %s\n' "$GLANCE_CHART_VERSION"
```
- `helm search repo ... --versions:` liệt kê các phiên bản chart Glance trong thông tin Helm repository trên máy.
- `|`: chuyển kết quả sang lệnh tiếp theo.
- `awk 'NR==2 {print $2}'`: lấy cột thứ hai của dòng thứ hai. Dòng đầu là tiêu đề; dòng thứ hai thường là phiên bản mới nhất trong kết quả.

### 3.1 Tải file overrides dành cho OpenStack 2026.1 và Ubuntu Noble
```bash
helm osh get-values-overrides \
  -d -p ~/osh-lab/overrides \
  -c glance 2026.1 ubuntu_noble
```

| Phần | Ý nghĩa |
|---|---|
| `helm osh get-values-overrides` | Lấy cấu hình overrides của OpenStack-Helm |
| `-d` | Tải các file overrides |
| `-p ~/osh-lab/overrides` | Thư mục lưu cấu hình |
| `-c glance` | Lấy cho chart Glance |
| `2026.1 ubuntu_noble` | Chọn cấu hình tương ứng bản OpenStack và hệ điều hành của image |

Tệp kết quả được lưu tại:
```
~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml
```
### 3.2. Truy vấn cấu hình storage và scheduling
```bash
helm show values openstack-helm/glance \
  --version "$GLANCE_CHART_VERSION" \
  | grep -n -A12 -B3 -E '^storage:|^volume:|^volume_staging:|^labels:|^  replicas:'
```
`helm show values` đọc values mặc định của chart phiên bản đã chọn.

Sau đó `grep` chỉ hiển thị những đoạn liên quan đến:
- `storage`: loại backend lưu image.
- `volume`: cấu hình volume.
- `volume_staging`: cấu hình volume staging.
- `labels`: cấu hình nhãn, chẳng hạn chọn node.
- `replicas`: cấu hình số bản sao ở mức thụt dòng được chỉ định.

Các tùy chọn của grep:

| Tùy chọn | Ý nghĩa |
|---|---|
| `-n` | Hiện số dòng |
| `-A12` | Hiện thêm 12 dòng sau dòng khớp |
| `-B3` | Hiện thêm 3 dòng trước dòng khớp |
| `-E` | Cho phép dùng biểu thức tìm kiếm với nhiều nhánh `\|` |
| `^` trong mẫu | Khớp từ đầu dòng |

## 4. Cơ chế post-render của Helm
Values chỉ tác động đến những trường được template của chart sử dụng. Khi chart không cung cấp tham số cho annotation hoặc nodeSelector, thay đổi có thể được thực hiện trong chart, trong manifests sau render hoặc tại thời điểm tài nguyên được tạo trong cụm. Post-renderer thuộc phương án xử lý manifests sau render.

Post-renderer là một chương trình bên ngoài mà Helm gọi sau khi render template xong và trước khi gửi lên cluster. Luồng như sau:

```
chart + values
     ↓ Helm render
YAML hoàn chỉnh ──(stdin)──► [post-renderer của bạn] ──(stdout)──► YAML đã sửa
                                                                        ↓
                                                                gửi lên K8s API
```
Helm truyền manifests qua stdin cho chương trình post-renderer. Chương trình điều chỉnh nội dung và trả manifests qua stdout; Helm sử dụng kết quả này để triển khai. Cơ chế đó cho phép bổ sung cấu hình mà không sửa template của chart.

Ví dụ sử dụng post-renderer:
```bash
helm upgrade --install myapp ./chart \
  -f values-prod.yaml \
  --post-renderer ./patch.sh
```
`patch.sh` có thể là bất cứ thứ gì đọc stdin và ghi stdout: shell script, sed, yq, Python... Cách phổ biến nhất là gọi Kustomize.

Post-renderer phải là một file thực thi (executable), không phải một chuỗi lệnh có sẵn tham số. Các bản Helm mới hơn có thêm cờ `--post-renderer-args` để truyền tham số.

Post-render là cơ chế tích hợp chương trình xử lý manifests. Kustomize là một trong các công cụ có thể được chương trình đó sử dụng; hai khái niệm này không tương đương.

Ví dụ sau minh họa giới hạn của values và vai trò của post-renderer:
- Giả sử template trong chart có dòng:
```yaml
replicas: {{ .Values.replicas }}
```
Trường replicas được template sử dụng nên có thể thay đổi qua values. Nếu template không đọc nodeSelector, việc bổ sung khóa sau vào values không làm manifests có thêm điều kiện chọn node:
```yaml
nodeSelector:
  disktype: ssd
```
Khóa đó không được template sử dụng nên không xuất hiện trong manifests sau render. Mỗi trường trong values phải được đối chiếu với template hoặc schema của chart để xác định tác dụng.
Các phương án điều chỉnh:

| Cách | Làm gì | Đánh đổi |
|-----|------|--------------|
| Sửa chart	`helm pull --untar`| Bổ sung nodeSelector vào template và triển khai chart tùy chỉnh |	Phần sửa phải được đối chiếu và áp dụng lại khi nâng chart|
| `Post-renderer`	| Chart giữ nguyên, sau khi render thì một chương trình ngoài thêm nodeSelector vào YAML |	Không đụng chart, nhưng thêm một script cần bảo trì |
| Kustomize	| Chính là công cụ thường được cắm vào post-renderer ở dòng trên để làm việc vá | Có thể xử lý trực tiếp manifests YAML không được sinh từ Helm|

## 5. Luồng triển khai dịch vụ trong Genestack
Genestack kết hợp Helm và Kustomize trong luồng triển khai dịch vụ:

```
chart openstack-helm  +  values (-f ...)
        ↓ helm render
   YAML hoàn chỉnh ──► kustomize.sh (post-renderer) ──► all.yaml
                                                          ↓ + resources thêm + patches
                                                  kubectl kustomize
                                                          ↓
                                                   gửi lên cluster
```
Script kustomize.sh được Helm gọi để xử lý manifests sau render.

```
BƯỚC 1: Helm
  chart Neutron (của người khác) + values (của Genestack)
        ↓
  ra một đống YAML: Deployment, Service, ConfigMap...

BƯỚC 2: Kustomize (khâu chỉnh sửa)
  nhận đống YAML đó, rồi
   • THÊM thứ chart không có (tạo database, tạo queue)
   • SỬA vài dòng chart không cho chỉnh
        ↓
  ra YAML cuối cùng

BƯỚC 3: gửi YAML cuối lên Kubernetes
```
Tham số --post-renderer bổ sung bước xử lý manifests giữa render và triển khai. Helm vẫn quản lý release sau khi nhận kết quả từ script.
Helm sinh manifests; cơ chế post-render gọi chương trình xử lý; Kustomize thực hiện các phép biến đổi YAML trong chương trình đó.

## 6. Các mô hình kết hợp Helm và công cụ xử lý manifests
Helm và Kustomize có thể được kết hợp ở nhiều vị trí trong quy trình. Các mô hình dưới đây khác nhau ở công cụ quản lý đầu ra và vòng đời release.
### 6.1. Helm gọi Kustomize qua post-renderer
Đây là mô hình post-renderer được sử dụng trong Genestack.
### 6.2. Kustomize sử dụng Helm làm nguồn manifests
Trường helmCharts trong kustomization.yaml khai báo tên chart, phiên bản và values. Kustomize gọi helm template để lấy manifests rồi áp dụng các phép biến đổi; tính năng này yêu cầu tham số --enable-helm.

Khi đầu ra được triển khai bằng kubectl apply, Helm chỉ đóng vai trò render. Không có Helm release tương ứng để quản lý bằng helm history hoặc helm rollback.

### 6.3. Tách render khỏi triển khai
```bash
helm template myapp ./chart -f values.yaml > all.yaml
# rồi kustomize build/kubectl kustomize lên all.yaml
```

Các công cụ GitOps cung cấp cơ chế phối hợp riêng. Flux hỗ trợ postRenderers trong HelmRelease; Argo CD hỗ trợ nguồn manifests từ Helm hoặc Kustomize. Chi tiết cấu hình được đối chiếu với tài liệu của phiên bản công cụ sử dụng. Các mô hình GitOps này chưa được nghiệm thu trong cụm tham chiếu.

### 6.4. Công cụ thay thế và phạm vi áp dụng
Một chương trình post-renderer phải đọc manifests từ stdin và trả kết quả hợp lệ qua stdout. Các công cụ có thể sử dụng gồm:
- `yq` hoặc `jq`: sửa field bằng một dòng lệnh, hợp với thay đổi nhỏ
- `sed`: thô sơ, dễ vỡ, chỉ nên dùng thay chuỗi đơn giản
- Script Python hoặc Go tự viết: khi logic phức tạp
- ytt (Carvel): ngôn ngữ template/overlay riêng, chuyên sửa YAML

Không dùng post-renderer, vẫn chỉnh được bằng cách khác:
- Sửa hoặc fork chart.
- Umbrella chart: chart tổng hợp khai báo chart gốc làm dependency, bổ sung values và các template riêng.
- Chỉnh ở phía cluster sau khi gửi lên: dùng admission controller như Kyverno hoặc OPA Gatekeeper để tự động thêm hoặc sửa field khi resource được tạo (ví dụ thêm nodeSelector cho mọi Deployment). Cách này không đụng vào bước Helm hay YAML nào cả.
