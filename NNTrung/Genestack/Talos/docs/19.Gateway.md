# Gateway API

```
Client
  │
  │ https://keystone.your.domain.tld
  ▼
F5 VIP
  │
  ▼
MetalLB VIP
  │
  ▼
Gateway Controller (ví dụ Envoy)
  │
  │ đọc hostname + HTTPRoute
  ▼
Kubernetes Service
  │
  ▼
Keystone Pod
```
- F5 nằm ngoài Kubernetes. F5 nhận traffic trước.
- Sau đó F5 forward traffic vào Kubernetes thông qua một IP do MetalLB cấp. MetalLB giúp Kubernetes có:
`Service type=LoadBalancer` trong môi trường bare-metal/private cloud.
- MetalLB VIP thực chất expose một Kubernetes Service của Gateway Controller.
- Tại gateway controller: Envoy nhận request: rồi dựa vào Gateway API resource: để quyết định: ví dụ `keystone.cloud.example.com -> keystone-api Service`

## 1. Gateway API
Trong Kubernetes trước đây người ta thường expose ứng dụng kiểu:
```
Ingress
Service
LoadBalancer
```
Nhưng Ingress khá hạn chế, Gateway API được thiết kế như thế hệ mới: Không có nghĩa Gateway API thay toàn bộ Kubernetes Service, mà là nó cung cấp một mô hình API chuẩn hơn để định nghĩa traffic đi vào/qua cluster như thế nào.
- Nó có thể xử lý routing ở:
```text
L4
TCP/UDP

L7
HTTP/HTTPS
hostname
path
header
TLS
...
```

```
Gateway API
= luật / cấu hình

Envoy
= thằng thực thi luật
```
## 2. Tại sao NextGen cần Gateway API
- Openstack có rất nhiều API tất cả dịch vụ Openstack đều cần API riêng
- Bên trong K8s bạn có thể:
```
keystone-api.openstack.svc.cluster.local
nova-api.openstack.svc.cluster.local
glance-api.openstack.svc.cluster.local
```
- Nhưng laptop/người dùng bên ngoài Kubernetes đâu có resolve hoặc truy cập trực tiếp các địa chỉ `.svc.cluster.local`.

Vì vậy cần một lớp phía trước:
```
keystone.cloud.example.com
nova.cloud.example.com
glance.cloud.example.com
```
Gateway API chịu trách nhiệm: Request hostname này phải được chuyển tới service nào? với mỗi OpenStack API cần expose, Genestack tạo route tương ứng.

## 2. Resource Models in Gateway API

| Type|	Description| 
|-------|------|
|GatewayClass| Represents a class of Gateway instances.|
| Gateway |	Represents a single Gateway instance.|
| HTTPRoute| Represents a set of HTTP-specific rules for mapping traffic to a backend.|
| Listener|	Represents a network endpoint that can accept incoming traffic.|

## 5. Hostname matching 
Đây là phần trung tâm của L7 routing.

Giả sử tất cả đều đi vào cùng một VIP:
```
192.168.100.50
```
Bạn không cần mỗi service một IP. Có thể:
```
keystone.cloud.example.com ─┐
nova.cloud.example.com ─────┤
glance.cloud.example.com ───┤
neutron.cloud.example.com ──┤
                            ▼
                       192.168.100.50
```
Gateway phân biệt chúng bằng hostname:
```
Host: keystone.cloud.example.com
→ Keystone

Host: nova.cloud.example.com
→ Nova

Host: glance.cloud.example.com
→ Glance
```
Đây là L7 HTTP routing. Nó giống virtual host của Nginx:
```
server_name keystone.example.com;
```
Gateway API chỉ chuẩn hóa khái niệm đó thành Kubernetes resources.

## 6. Envoy Gateway API
The Envoy Gateway is an open-source project that provides an **implementation** of the Gateway API using Envoyproxy as the data plane.
```
Gateway API
= tiêu chuẩn / ngôn ngữ cấu hình

Envoy Gateway
= phần mềm hiểu tiêu chuẩn đó

Envoy Proxy
= thằng thực sự nhận và forward request
```
### 6.1 Installation
Run the helm command to install Envoy Gateway: 
```bash
/opt/genestack/bin/install-envoy-gateway.sh`
```
```
install-envoy-gateway.sh
        ↓
Helm
        ↓
Envoy Gateway controller
        ↓
Kubernetes namespace
```
### 6.2 Setup
Cấu hình Gateway thực sự cho Genestack.
```bash
/opt/genestack/bin/setup-envoy-gateway.sh
```
Họ dùng email xác thực

The setup script will ask the following questions:
- Enter a valid email address for use with ACME, press enter to skip"
- Enter the domain name for the gateway"

Nhớ gateway API là luật còn người đọc và thực thi nó là Envoy Gateway API

### 6.3 Validation
At this stage, Envoy Gateway should be operational. To validate the configuration, run the following command.
```bash
kubectl -n openstack get httproute

kubectl -n envoy-gateway get gateways.gateway.networking.k8s.io flex-gateway
```
Troubleshooting:

If you encounter any issues, check the logs of the envoy-gateway deployment.
```bash
kubectl logs -n envoyproxy-gateway-system deployment/envoy-gateway
```

## 7. Envoy Gateway Internal and External Gateway
Genestack can deploy Envoy Gateway in the original single gateway mode or in multi-gateway config mode.

The original mode creates one `flex-gateway`(Chỉ có duy nhất 1 cổng dùng chung cho tất cả các svc). Config mode creates separate gateways, usually named `external` and `internal`, with separate GatewayClasses, MetalLB pools, listeners, certificates, and HTTPRoutes.

```
                         Internet / User
                               |
                               v
                      +------------------+
                      | External Gateway |
                      +------------------+
                               |
                  Keystone / Horizon / API
                               |
                               v
                         Kubernetes


Admin / Monitoring network
          |
          v
 +------------------+
 | Internal Gateway |
 +------------------+
          |
     Prometheus
     Grafana
     Internal API
```

Use config mode when routes need to be explicitly published as:
- `external`: reachable through the external gateway only. có thể được Internet hoặc client bên ngoài truy cập.
- `internal`: reachable through the internal gateway only. Internet sẽ không đi vào đường này.
- `both`: rendered for both gateways. Tức là cùng một service sẽ được tạo route trên cả external lẫn internal gateway. Có thể dùng khi: Keystone vừa cần phục vụ client bên ngoài, vừa cần phục vụ hệ thống nội bộ.
- `skip`: intentionally not rendered in the new config. Không tạo route cho service đó trong cấu hình Gateway mới.

The generated configuration file is normally:
```bash
/etc/genestack/envoy-gateways.yaml
```
