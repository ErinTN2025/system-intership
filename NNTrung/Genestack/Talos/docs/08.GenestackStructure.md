# Sử dụng Genestack theo workflow: từ repo đến cloud chạy được

## Khái niệm cần nắm trước

Genestack tách làm hai nơi:

- **`/opt/genestack`**: bản clone của repo, coi như **chỉ đọc**. Không sửa trực tiếp ở đây.
- **`/etc/genestack`**: nơi **bạn chỉnh cấu hình**. `bootstrap.sh` tạo nó từ repo, và các script cài đặt ưu tiên file ở đây hơn file mặc định trong repo.

File zip bạn gửi có thư mục `submodules/` rỗng vì GitHub không đóng gói submodule. Khi dùng thật phải `git clone --recurse-submodules` để có Kubespray.

## Bước 0: Chọn nơi dựng (nếu chỉ muốn thử)

- Tra cứu: `docs/build-test-envs.md`
- Dùng: `scripts/hyperconverged-lab*.sh` (lab gộp mọi vai trò vào ít node, hỗ trợ cả Kubespray lẫn Talos) và `testing/` (template Heat dựng VM thử trên một OpenStack có sẵn)

## Bước 1: Lấy code và bootstrap

- Tra cứu: `docs/genestack-getting-started.md`, `README.md`
- Chạy `bootstrap.sh`. Script này cài package, `yq`, `helm`, `cmctl`, tạo venv `~/.venvs/genestack`, cài Ansible theo `requirements.txt` và `ansible-collection-requirements.yml`, rồi dựng `/etc/genestack` gồm:
  - `inventory/` (chép từ `ansible/inventory/genestack/`)
  - `helm-configs/<service>/` và `global_overrides/` (thư mục rỗng, để bạn đặt override)
  - `manifests/` và `helm-chart-versions.yaml` (bản chép từ repo)
  - `kustomize/<service>/` (symlink tới `base-kustomize/`, kèm thư mục `overlay/` tự tạo)
  - lệnh `ye` (từ `yaml-editor/`)
- `scripts/genestack.rc`: file biến môi trường, mỗi lần mở shell mới nên `source` nó (nó trỏ `ANSIBLE_INVENTORY` về `/etc/genestack/inventory`).

## Bước 2: Khai báo máy và mạng

- Tra cứu: `docs/k8s-kubespray.md`, `docs/k8s-overview.md`
- Sửa `/etc/genestack/inventory/` theo mẫu `ansible/inventory/genestack/inventory.yaml.example` và `group_vars/`.
- `etc/netplan/default.yaml` là mẫu cấu hình mạng host. Doc yêu cầu tối thiểu **2 network interface**, kernel 5.17+, `/tmp` không `noexec`. Phần này liên quan trực tiếp tới chuyện hai dải mgmt/tunnel mà bạn hỏi.

## Bước 3: Dựng Kubernetes

- Chạy `ansible/playbooks/host-setup.yml` (chuẩn bị host, role nằm trong `ansible/roles/`), rồi `cd submodules/kubespray && ansible-playbook cluster.yml --become`.
- Tra cứu: `docs/k8s-kubespray.md`, hoặc `docs/k8s-talos.md` nếu dùng Talos.
- Cấu hình CNI: `docs/k8s-cni-kube-ovn.md` và `base-helm-configs/kube-ovn/kube-ovn-helm-overrides.yaml`. Theo doc, giá trị thường chỉ cần đặt là `IFACE` (và `VLAN_INTERFACE_NAME`), tức đúng chỗ chọn NIC tunnel. Repo cũng có doc và script chuyển Kube-OVN từ kiểu cài cũ sang Helm (`docs/k8s-cni-kube-ovn-helm-conversion.md`, `scripts/kube-ovn-convert.sh`).

## Bước 4: Gắn label và annotation cho node

- Tra cứu: `docs/k8s-labels.md`, `docs/infrastructure-ovn-setup.md`
- Label vai trò: `openstack-control-plane`, `openstack-compute-node`, `openstack-network-node`, `openstack-storage-node`, `kube-ovn/role=master`...
- Annotation OVN `ovn.openstack.org/*`: `bridges` (br-ex), `mappings` (physnet1:br-ex), `ports`, `bonds`, `vlans`, `availability_zones`, và **`gateway: enabled`** để đánh dấu node gateway. Đây chính là chỗ ứng với chuyện "gộp node gateway vào worker" mà ta đã nói.
- Đổi sau khi cài: `docs/ovn-kube-ovn-openstack.md` (gỡ label `ovn.openstack.org/configured` để DaemonSet `ovn-setup` áp dụng lại).

## Bước 5: Cài hạ tầng nền

Có hai cách: chạy từng bước theo `docs/infrastructure-*.md`, hoặc chạy gộp `bin/setup-infrastructure.sh` (hỏi bạn domain và interface). Thứ tự trong script:

Kube-OVN → Longhorn → kube-prometheus-stack → cert-manager → MetalLB → namespace `openstack` (`kubectl apply -k .../kustomize/openstack/base`) → Envoy Gateway → secrets (`/etc/genestack/kubesecrets.yaml`) → MariaDB operator → RabbitMQ operator và cluster → `kustomize/ovn/base` → Memcached → Libvirt → Redis.

- Mỗi thành phần có file `bin/install-<tên>.sh`, `base-helm-configs/<tên>/`, `base-kustomize/<tên>/`.
- Phần hạ tầng ngoài Helm dùng `manifests/` (longhorn, metallb, swift, grafana, utils) và `etc/gateway-api/` (mẫu listener, route, Let's Encrypt). `examples/envoy-multi-gateway-config.yaml` là ví dụ nhiều gateway.
- Secret: có `bin/create-secrets.sh`; script cài thấy tái dùng `kubesecrets.yaml` nếu đã tồn tại.

## Bước 6: Cài OpenStack

- Chạy `bin/setup-openstack.sh` hoặc từng `bin/install-<service>.sh`, tra cứu `docs/openstack-*.md`. Thứ tự: keystone → glance, heat, barbican, ... → placement → nova → neutron → ... → ironic, skyline.
- `openstack-components.yaml` quyết định service nào bật (mặc định `true` cho barbican, glance, keystone, neutron, nova, placement, skyline). Theo comment trong file, nó dùng cho lab hyperconverged.
- **Cơ chế bên trong mỗi `install-*.sh`** (đúng cái bạn học về Helm + Kustomize): đọc version chart từ `helm-chart-versions.yaml`, gom `-f` từ `base-helm-configs/<svc>/` + `/etc/genestack/helm-configs/<svc>/` + `global_overrides/`, rồi `helm upgrade --install` với post-renderer `kustomize.sh`.
- Riêng `install-neutron.sh` đọc `ENABLE_SSL` của Kube-OVN để chọn kết nối OVN `ssl` hay `tcp` (chi tiết như mình đã nêu ở lần trước).

## Bước 7: Tùy biến (vòng lặp bạn sẽ làm nhiều nhất)

| Muốn đổi | Sửa ở đâu |
|---|---|
| Giá trị chart cho phép | `/etc/genestack/helm-configs/<svc>/` (có công cụ `ye <svc>`: gộp base + override để sửa một chỗ, lưu thì chỉ ghi phần override) |
| Áp dụng cho mọi service | `/etc/genestack/helm-configs/global_overrides/` |
| Version chart | `/etc/genestack/helm-chart-versions.yaml` |
| Thêm resource hoặc vá thứ chart không có | `/etc/genestack/kustomize/<svc>/overlay/kustomization.yaml` |

Không sửa `base-helm-configs/` hay `base-kustomize/` trong `/opt`, vì đó là bản gốc, bạn chỉ đè lên ở `/etc`.

## 1. Chọn điểm bắt đầu: dựng mới hay tiếp tục file 05?

**Mục tiêu:** tránh cài đè một hệ thống đang có mà chưa biết phần nào được giữ lại.

Nếu dựng cloud mới, đi theo bước 2 đến hết. Nếu đang có lab từ file 05, trước hết ghi lại trạng thái:

```bash
kubectl config current-context
kubectl get nodes -o wide
helm list -A
kubectl get pods -A
kubectl get storageclass
kubectl get pv,pvc -A
```

Đối chiếu các phần đã cài: Kube-OVN, MariaDB, RabbitMQ, Glance, Nova, Neutron, libvirt, Ceph/Rook và Cinder. Ghi lại release name, namespace, chart version, values và backend dữ liệu.

## 2. Chốt thiết kế trước khi cài

**Mục tiêu:** biết mình đang xây cloud nào để chọn cấu hình đúng.

Ghi một bảng thiết kế của môi trường:

| Quyết định | Ví dụ câu hỏi cần trả lời |
| --- | --- |
| Node | Node nào chạy API, compute, network gateway, storage? Có chạy nhiều vai trò chung một node không? |
| Compute | Node compute có `/dev/kvm` không? Nếu là VM, nested virtualization đã bật chưa? |
| Mạng | NIC quản trị, NIC/provider VLAN là gì? `physnet` và bridge mapping nào sẽ dùng? |
| Storage Kubernetes | PVC của DB/MQ dùng local-path, Longhorn hay Ceph CSI? |
| Storage OpenStack | Glance lưu image ở đâu? Nova lưu đĩa instance ở đâu? Cinder dùng backend nào? |
| Endpoint | Domain, địa chỉ gateway/load balancer và TLS là gì? |
| Dịch vụ | Cần bộ VM cơ bản hay thêm Cinder, Octavia, Magnum, Manila...? |
| Khả năng chịu lỗi | Lab một replica hay nhiều node/replica? Backup ở đâu? |

Đọc theo nhu cầu, không cần đọc cả `docs/` từ đầu đến cuối:

- [Thiết kế cloud](../../genestack/docs/openstack-cloud-design-intro.md).
- [Topology](../../genestack/docs/openstack-cloud-design-topology.md).
- [Storage overview](../../genestack/docs/storage-overview.md).
- [Kube-OVN và OpenStack](../../genestack/docs/ovn-kube-ovn-openstack.md).
- [Danh sách thành phần](../../genestack/docs/genestack-components.md).

**Đầu ra:** bảng thiết kế đã có câu trả lời. Nếu chưa biết đường dẫn dữ liệu VM hoặc NIC provider, chưa chuyển sang cài Nova/Neutron.

## 3. Chuẩn bị repo và máy quản trị Linux

**Mục tiêu:** có mã nguồn, dependencies và cấu trúc cấu hình mà script cần.

Bắt đầu bằng [genestack-getting-started.md](../../genestack/docs/genestack-getting-started.md), rồi đọc [bootstrap.sh](../../genestack/bootstrap.sh).

Với máy quản trị mới chưa có checkout:

```bash
# Chỉ clone khi chưa có repo tại đường dẫn này.
git clone --recurse-submodules -j4 https://github.com/rackerlabs/genestack /opt/genestack
cd /opt/genestack
git submodule status
```

Nếu đã có checkout thì không clone đè; kiểm tra revision và submodules hiện có. `.gitmodules` khai báo `submodules/kubespray` và `submodules/openstack-exporter`.

Khi đã chọn revision phù hợp cho môi trường:

```bash
sudo -E /opt/genestack/bootstrap.sh
source /opt/genestack/scripts/genestack.rc
```

Bootstrap có cài package, tạo Python virtualenv, chuẩn bị Ansible, tạo inventory, thư mục overrides, liên kết Kustomize và copy một số cấu hình nền. Nó **không có nghĩa cloud OpenStack đã được cài xong**.

Các file nên mở để hiểu bước này:

| File | Bạn tìm thông tin gì? |
| --- | --- |
| `bootstrap.sh` | Máy quản trị sẽ bị thay đổi thế nào, file nào được tạo/copy? |
| `scripts/genestack.rc` | Biến cấu hình, inventory, provider và kích hoạt virtualenv. |
| `scripts/lib/functions.sh` | Các hàm hỗ trợ bootstrap, dependencies. |
| `requirements.txt` | Dependencies Python. |
| `requirements.yml`, `ansible-collection-requirements.yml` | Dependencies Ansible. |

Kiểm tra sau bootstrap:

```bash
command -v helm kubectl ansible-playbook
ls /etc/genestack
ls /etc/genestack/helm-configs
ls /etc/genestack/kustomize
cat /etc/genestack/provider
```

**Đầu ra:** máy quản trị có công cụ và cấu hình runtime. Provider mặc định có thể là Kubespray; bootstrap có nhiều đường dẫn cố định `/opt/genestack`, `/etc/genestack`, nên không giả định đổi một biến là đổi được tất cả đường dẫn.

## 4. Đảm bảo cluster Kubernetes/Talos hoạt động

**Mục tiêu:** máy quản trị truy cập được đúng cluster trước khi cài workload.

### Luồng Talos của bạn

Đọc [k8s-talos.md](../../genestack/docs/k8s-talos.md), kết hợp tài liệu [cài Talos](01.InstallTalos.md), [Talosctl](02.TalosctlCommands.md), [CNI](03.TalosCNI.md) và [disk](04.CreateDisk.md).

Nếu cluster đã có từ file 05, kiểm tra kubeconfig và trạng thái hiện tại. Nếu chưa có, làm luồng tạo machine config, apply config, bootstrap etcd một lần và lấy kubeconfig theo tài liệu Talos. Đối chiếu cấu hình CNI trước khi bootstrap để không triển khai chồng hai CNI.

```bash
kubectl config current-context
kubectl cluster-info
kubectl get nodes -o wide
kubectl get pods -n kube-system
```

Khi CNI đã hoạt động, node cần đạt Ready; DNS và workload hệ thống cần hoạt động trước khi cài API OpenStack. Nếu đang chủ động để cluster chờ cài CNI, trạng thái chưa Ready phải được giải quyết ở bước mạng, không bỏ qua rồi tiếp tục cài dịch vụ.

### Nếu dùng Kubespray thay vì Talos

Đi từ `ansible/inventory/`, cấu hình runtime `/etc/genestack/inventory`, đọc [k8s-kubespray.md](../../genestack/docs/k8s-kubespray.md) và role/playbook liên quan.

**`bin/setup-hosts.sh` gọi `host-setup.yml` rồi `submodules/kubespray/cluster.yml`; đây là nhánh Kubespray, không phải lệnh để dựng node Talos.**

### Nếu muốn dựng lab Talos tự động

Đọc `scripts/hyperconverged-lab-talos.sh` và `scripts/lib/hyperconverged-common.sh`. Luồng này tạo lab trên cloud OpenStack, có image, mạng, VM và jump host; không phải script chỉ kết nối tới hai node Talos hiện có của bạn.

**Đầu ra:** truy cập đúng cluster và biết nhánh triển khai Kubernetes nào đang sử dụng.

## 5. Gán vai trò node: workload sẽ chạy ở đâu?

**Mục tiêu:** labels khớp với thiết kế bước 2 và node selector của chart.

Đọc [k8s-labels.md](../../genestack/docs/k8s-labels.md), [k8s-taint.md](../../genestack/docs/k8s-taint.md) rồi xem selectors trong `base-helm-configs/<dịch-vụ>/`.

| Label | Quyết định placement nào? |
| --- | --- |
| `openstack-control-plane=enabled` | API/control services của OpenStack. |
| `openstack-compute-node=enabled` | Nova compute/libvirt. |
| `openstack-network-node=enabled` | Thành phần mạng OpenStack; compute cũng có thể cần vai trò này khi dùng OVN. |
| `openstack-storage-node=enabled` | Thành phần storage. |
| `longhorn.io/storage-node=enabled` | Node tham gia storage Longhorn. |
| `openstack-ovn-vpn-agent=enabled` | Chỉ cho gateway node chạy VPN agent khi dùng VPNaaS. |

Ví dụ cách gán, thay tên node theo thiết kế:

```bash
kubectl label node <api-node> openstack-control-plane=enabled --overwrite
kubectl label node <compute-node> openstack-compute-node=enabled --overwrite
kubectl label node <compute-node> openstack-network-node=enabled --overwrite
kubectl get nodes --show-labels
```

Không đồng nhất Kubernetes control plane với OpenStack control plane: một bên quản lý cluster, một bên phục vụ cloud. Bạn có thể đặt cùng node trong lab nhưng phải chọn có chủ đích.

**Đầu ra:** các workload có node phù hợp để schedule; hiểu taint nào sẽ chặn chúng. `setup-infrastructure.sh` có thao tác đổi labels và gỡ taint, cần đọc trước khi dùng.

## 6. Chuẩn bị cấu hình môi trường trước khi gọi installer

**Mục tiêu:** biến baseline của repo thành cấu hình cho cloud của bạn.

Mở [genestack-structure-and-files.md](../../genestack/docs/genestack-structure-and-files.md), một script như [install-glance.sh](../../genestack/bin/install-glance.sh), rồi lần theo đường dẫn nó đọc.

```text
/opt/genestack/base-helm-configs/glance/        cấu hình nền
/etc/genestack/helm-configs/global_overrides/  cấu hình chung của cloud
/etc/genestack/helm-configs/glance/            cấu hình riêng Glance
/etc/genestack/helm-chart-versions.yaml        chart version đang dùng
/etc/genestack/kustomize/glance/overlay/      tùy biến manifest
```

### 6.1. Chốt phiên bản chart

Xem `helm-chart-versions.yaml` ở repo và bản runtime. Script cài dịch vụ thường đọc bản runtime. Bootstrap không tự ghi đè file runtime đã tồn tại, nên cập nhật Git chưa đồng nghĩa chart version đã đổi.

### 6.2. Viết Helm overrides

Ví dụ bạn muốn Glance dùng backend cụ thể:

1. Đọc `docs/openstack-glance.md` và tài liệu backend tương ứng.
2. Xem `base-helm-configs/glance/` để biết Genestack đang đặt gì.
3. Xem values của đúng chart version để biết các key được hỗ trợ.
4. Ghi phần thay đổi vào `/etc/genestack/helm-configs/glance/99-local-overrides.yaml`.
5. Kiểm tra script `install-glance.sh` thực sự nạp file đó.

Với các script đã đối chiếu như Keystone/Glance, thứ tự là baseline → global overrides → service overrides → các giá trị `--set` từ script. Khi nhiều file cùng đặt một key, lớp sau được ưu tiên. Đọc script của dịch vụ cụ thể để xác nhận hành vi.

`yaml-editor/ye` là lựa chọn hỗ trợ chỉnh values, ví dụ `ye nova`; đọc `yaml-editor/README.txt` trước khi dùng. Bạn cũng có thể tự sửa YAML bằng editor.

### 6.3. Viết Kustomize overlay khi values chưa đủ

Nếu cần thêm manifest hoặc patch tài nguyên, đọc `base-kustomize/<dịch-vụ>/base/` và chỉnh overlay runtime. Overlay có thể tham chiếu `../base`, `../aio` hoặc cấu hình khác tùy thành phần; phải kiểm tra thư mục đó thực sự tồn tại.

Bootstrap tạo nhiều symlink về repo. Dùng `ls -l`/`readlink -f` để biết mình đang sửa file riêng hay tài nguyên trong checkout.

**Liên hệ file 05:** `~/osh-lab/overrides` tương ứng ý tưởng với `helm-configs`, nhưng không tự động được Genestack đọc. Muốn dùng lại, phải chuyển các cấu hình cần thiết sang đường dẫn installer sử dụng, đồng thời đối chiếu baseline Genestack để tránh xung đột.

**Đầu ra:** phiên bản, values và overlays đã phản ánh thiết kế. Các đường dẫn dữ liệu Glance/Nova/Cinder phải được xác định riêng, không coi PVC của DB là backend cho mọi dữ liệu cloud.

## 7. Tạo namespace và secrets

**Mục tiêu:** có namespace và thông tin xác thực mà installer đọc.

Đọc [infrastructure-namespace.md](../../genestack/docs/infrastructure-namespace.md), `base-kustomize/openstack/base/` và `bin/create-secrets.sh`.

Luồng tài liệu cho môi trường mới:

```bash
kubectl apply -k /etc/genestack/kustomize/openstack/base
/opt/genestack/bin/create-secrets.sh
# File sinh ra chứa credentials, phải lưu và bảo vệ theo môi trường.
kubectl create -f /etc/genestack/kubesecrets.yaml
```

Script hỗ trợ chọn region; đọc tham số trong script nếu không dùng RegionOne. Với cluster có secrets rồi, kiểm tra tên và nguồn trước; không chạy lại việc sinh credentials như thể đang dựng mới.

Đọc `bin/install-<dịch-vụ>.sh` để biết nó lấy Secret nào. Ví dụ installer có thể cần mật khẩu Keystone, MariaDB, RabbitMQ và mật khẩu DB riêng của dịch vụ. Secret do operator sinh có thể chỉ xuất hiện sau khi DB/MQ được tạo ở bước 8.

Kiểm tra tên Secret, không cần in giá trị mật khẩu:

```bash
kubectl get namespace openstack
kubectl -n openstack get secrets
```

**Đầu ra:** namespace đúng và các credentials ban đầu có mặt; phân biệt Secret tự tạo với Secret operator sẽ tạo sau.

## 8. Dựng hạ tầng mà OpenStack phụ thuộc

**Mục tiêu:** mạng, lưu trữ, DB/MQ/cache và compute runtime sẵn sàng trước khi cài API OpenStack.

Mở `bin/setup-infrastructure.sh` như bản đồ triển khai. Script hiện tại có các bước: labels/taints và annotations mạng, Kube-OVN, Longhorn, monitoring, cert-manager, MetalLB/Envoy, MariaDB operator/cluster, RabbitMQ operators/cluster, OVN setup, Memcached, libvirt và Redis.

Có hai cách sử dụng:

- **Dựng mới và chọn đúng baseline của script:** cấu hình đầu vào, đọc toàn bộ script rồi dùng nó để điều phối.
- **Lab đã có CNI/storage/DB từ file 05 hoặc chọn backend khác:** đi từng thành phần theo tài liệu và lệnh bên trong script. Script không phải công cụ tự nhận diện và giữ nguyên mọi hệ thống sẵn có.

### 8.1. CNI và mạng OpenStack

Đọc `docs/k8s-cni-kube-ovn.md`, `docs/infrastructure-ovn-setup.md`, `base-helm-configs/kube-ovn/`, `base-kustomize/ovn/base/ovn-setup.yaml`.

Các điểm phải khớp: địa chỉ cluster, interface/VLAN, bridge `br-ex`, physnet mapping, gateway node và kết nối NB/SB. Baseline Neutron dùng OVN, tắt OVS agent truyền thống; phần shared OVN cuối file 05 gần hướng này hơn đoạn thử VXLAN/OVS agent trước đó.

Kiểm tra node Ready, Pod CNI, DNS và bridge/mapping thực tế trước khi chuyển tiếp. Không chạy lại installer Kube-OVN với values khác mà chưa đối chiếu CNI đang hoạt động.

### 8.2. Storage cho PVC và backend OpenStack

Đọc tài liệu backend đã chọn trong `docs/storage-*.md`. Luồng tổng hợp cài Longhorn, nhưng repo cũng có Rook/Ceph và TopoLVM. `manifests/longhorn/` chứa namespace/StorageClass bổ trợ; các cấu hình Rook nằm trong `base-kustomize/rook-*/`.

```bash
kubectl get storageclass
kubectl get pv,pvc -A
```

Kiểm tra bằng một PVC/Pod thử ghi và đọc lại, như bài test trong file 05. Xác định dữ liệu có giữ qua restart và phụ thuộc node nào. Ceph cho Cinder và StorageClass cho PVC là các quyết định liên quan nhưng không đồng nhất.

`scripts/import-external-cluster.sh` dùng cho Ceph external/Rook; không phải lệnh nhập cluster Kubernetes bất kỳ.

### 8.3. MariaDB, RabbitMQ và Memcached

| Thành phần | Đọc trước | Nơi thực hiện/cấu hình |
| --- | --- | --- |
| MariaDB | `docs/infrastructure-mariadb.md` | `bin/install-mariadb-operator.sh`, `base-kustomize/mariadb-cluster/`, overlay runtime. |
| RabbitMQ | `docs/infrastructure-rabbitmq.md` | `base-kustomize/rabbitmq-operator/`, `rabbitmq-topology-operator/`, `rabbitmq-cluster/`. |
| Memcached | `docs/infrastructure-memcached.md` | `bin/install-memcached.sh`, `base-helm-configs/memcached/`. |

Cài operator trước, chờ operator/webhook sẵn sàng rồi tạo tài nguyên cluster. Với lab nhỏ, xem cấu hình `aio` của từng thành phần thay vì giữ số replicas lớn rồi để Pod Pending.

Kiểm tra Pod, PVC, tài nguyên custom và Secret operator sinh. Đây là dependencies mà installer OpenStack sẽ truy cập.

### 8.4. libvirt và dữ liệu Nova

Đọc `docs/infrastructure-libvirt.md`, `bin/install-libvirt.sh`, `base-helm-configs/libvirt/`, `docs/openstack-compute-kit-nova.md`.

Kiểm tra KVM, đường dẫn đĩa instance trên host, OVSDB và khả năng chạy workload privileged trên Talos. Nếu dùng Ceph/RBD, đọc luồng Ceph cho Nova/libvirt và cách nạp credentials tồn tại qua restart. Lệnh sửa trong container như cuối file 05 cần được chuyển thành cấu hình triển khai bền vững.

### 8.5. Endpoint, gateway và TLS

Đọc `docs/infrastructure-metallb.md`, `docs/infrastructure-envoy-gateway-api.md`, `docs/infrastructure-cert-manager.md`. Tra cấu hình tại `etc/gateway-api/`, ví dụ trong `examples/`, script `setup-envoy-gateway.sh` và `install-envoy-gateway.sh`.

Xác định pool IP, domain và TLS phù hợp mạng của bạn. `etc/netplan/` là mẫu cho host Linux phù hợp; trên Talos phải chuyển ý định cấu hình NIC sang machine config/API Talos.

**Điều kiện sang bước 9:** CNI/DNS hoạt động, storage cấp được PVC, DB/MQ/cache có thể sử dụng, libvirt có node compute phù hợp và credentials dependencies có mặt. Có thể chỉ cài các thành phần cần thiết, nhưng không bỏ qua dependency của dịch vụ đã chọn.

## 9. Cài dịch vụ OpenStack: bắt đầu Keystone

**Mục tiêu:** triển khai dịch vụ trên hạ tầng đã chuẩn bị.

### 9.1. Chọn bộ dịch vụ

Xem `openstack-components.yaml` ở repo, rồi chuẩn bị bản runtime mà `bin/setup-openstack.sh` đọc, mặc định `/etc/genestack/openstack-components.yaml`. Nếu chưa có file, script có luồng hỏi lựa chọn. Có file rồi thì đối chiếu giá trị với nhu cầu.

Bộ cloud VM thường cần Keystone, Glance, Placement, Nova, Neutron; dashboard và các dịch vụ khác chọn theo nhu cầu. Cinder thêm volume, Octavia thêm load balancer, Magnum thêm quản lý cluster, Manila thêm shared filesystem.

**Chi tiết từ mã nguồn:** script hiện tại luôn gọi Keystone trước, dù file components có mục Keystone. Sau đó nhiều dịch vụ được chạy song song, Ironic được trì hoãn tới sau dependencies, Skyline chạy cuối. Trove được ghi chú không cài trong đoạn điều phối này.

### 9.3. Installer thay bạn làm những gì?

Lần theo `install-glance.sh`:

```text
Đọc chart version trong /etc/genestack
→ chọn repository/chart
→ gom baseline + global values + service values
→ lấy credentials từ Kubernetes Secret
→ Helm render
→ Kustomize post-renderer áp overlay
→ helm upgrade --install gửi kết quả vào cluster
```

Đây là điểm nối với file 05: các lệnh Helm thủ công được gói vào script có quy ước cấu hình.

Nếu muốn xem trước, dựng lệnh `helm template` theo đúng chart version, namespace, toàn bộ values và tham số mà installer dùng. Bỏ qua `--set` credentials hoặc post-renderer có thể cho kết quả khác bản cài thật. `base-kustomize/kustomize.sh` ghi manifest render vào `all.yaml`, nên render có post-renderer cũng có thể ghi file trên máy quản trị.

**Không coi chạy installer với `--dry-run` là luôn chỉ đọc:** installer có thể cập nhật Helm repo hoặc làm bước phụ trước Helm; đọc script trước khi dùng.

**Đầu ra:** releases và workloads ổn định, jobs khởi tạo/schema hoàn thành. Nếu Job lỗi, giải quyết lỗi đó trước thay vì tiếp tục cài các dịch vụ phụ thuộc.

## 11. Kiểm chứng toàn bộ đường đi

**Mục tiêu:** phân biệt “Pod Running” với “cloud dùng được”.

Kiểm tra tối thiểu:

1. Tạo VM nhỏ, kiểm tra status/fault và hypervisor nhận VM.
2. Vào console, kiểm tra IP, DHCP, route và DNS trong VM.
3. Thử traffic giữa VM và ra mạng ngoài nếu đã cấu hình external network.
4. Nếu có Cinder, tạo/attach volume và kiểm tra thiết bị trong VM.
5. Kiểm tra restart dịch vụ không làm mất credentials hoặc dữ liệu theo thiết kế.
6. Kiểm tra access qua endpoint/domain dự kiến, không chỉ port-forward.

Tra `docs/ovn-traffic-flow-intro.md`, `docs/ovn-troubleshooting.md`, tài liệu dịch vụ và các bước kiểm tra trong file 05.

Repo có `bin/install-tempest.sh`, `base-helm-configs/tempest/` và `base-kustomize/tempest/` cho kiểm thử OpenStack khi cần phạm vi rộng hơn. `testing/` chủ yếu phục vụ dựng môi trường thử nghiệm, không thay thế bài kiểm tra cloud người dùng.

**Đầu ra:** một danh sách kiểm chứng đã đạt, kèm các giới hạn của lab như local storage, một replica hoặc nested virtualization.

### 12.3. Khi gặp lỗi, đi theo dấu vết này

```text
VM/API lỗi
→ logs/events của workload
→ release và values đang áp dụng
→ script installer lấy input nào
→ file runtime nào tạo giá trị đó
→ baseline/chart/operator tương ứng
```

```bash
kubectl -n openstack get pods,jobs,pvc
kubectl -n openstack get events --sort-by=.metadata.creationTimestamp

kubectl -n openstack logs <pod-name> --all-containers --tail=100
helm -n openstack status <release-name>
```

`helm get values`/`helm get manifest` có thể chứa credentials; dùng cục bộ khi cần và kiểm tra trước khi chia sẻ output.

Mở `ops-tools/README.md` rồi README của công cụ đúng lỗi: `ovn/`, `check_octavia_ovn/`, `find_orphan_instances/`, `find_orphan_qdisk/`, `rogue_pod_scanner/`, `image_uuid_migrations/`. Tên công cụ không bảo đảm chỉ đọc; kiểm tra các thao tác sửa/xóa trước khi dùng.

`scripts/` còn có rotation passwords, quản lý HPA, kiểm tra multipath, dọn jobs và sửa các tình huống vận hành. Chọn script theo vấn đề đã xác định, đọc tham số và dependencies trước.

### 12.4. Khi thêm node

Đọc `docs/adding-new-node.md`; áp dụng phần phù hợp provider. Với Talos, thêm machine config/node bằng Talos trước, sau đó gán labels, storage/mạng và kiểm tra workload. Inventory/Ansible của Kubespray không tự thay thế luồng Talos.

**Đầu ra:** có theo dõi, backup được kiểm chứng và cách tìm lỗi không phụ thuộc vào sửa tay trong container.

## 13. Nâng cấp: đừng chỉ Git pull rồi chạy tất cả

**Mục tiêu:** thay đổi có thể kiểm chứng và có phương án phục hồi.

1. Ghi lại revision hiện tại, chart versions, image tags, overrides, operator versions và trạng thái cloud.
2. Backup dữ liệu/cấu hình và chọn phiên bản đích.
3. Đọc `docs/genestack-upgrade.md`, release notes trong `docs/`, `dist/`, ghi chú trong `releasenotes/notes/`.
4. Tìm quy trình tương ứng trong `maintenances/`, ví dụ nâng MariaDB, RabbitMQ, Longhorn hoặc OpenStack services.
5. So sánh baseline mới với runtime: file versions/overrides đã tồn tại không tự được bootstrap thay thế.
6. Kiểm tra dependencies, schema/CRD, image và storage; nâng theo quy trình thành phần.
7. Chạy lại các bài kiểm chứng bước 11 và theo dõi metrics/logs.

Helm rollback không tự phục hồi DB schema, dữ liệu volume hoặc mọi tài nguyên do operator quản lý. Phương án rollback phải dựa trên loại thay đổi thực tế.

**Đầu ra:** phiên bản đã cập nhật, cloud vẫn hoạt động và thay đổi được ghi lại. `maintenances/` là runbook cho tình huống cụ thể, không phải thư mục cần chạy lúc cài lần đầu.

## 14. Khi cần sửa Genestack thay vì chỉ sửa môi trường

**Mục tiêu:** biết lúc nào làm việc với mã nguồn và các thư mục phát triển.

| Nhu cầu | Làm ở đâu và theo thứ tự nào? |
| --- | --- |
| Chỉ đổi cấu hình cloud của bạn | Sửa `/etc/genestack/helm-configs/` hoặc overlay runtime; kiểm chứng dịch vụ. |
| Sửa baseline cho các lần triển khai khác | `base-helm-configs/`, `base-kustomize/`; thử trong môi trường riêng rồi ghi chú thay đổi. |
| Thêm installer dịch vụ | Đọc `bin/install-service-template.sh`, thêm script và dependencies/config tương ứng. |
| Thêm tự động hóa hạ tầng | `ansible/playbooks/`, lần theo `roles/`, `filter_plugins/` và vars. |
| Build image có patch riêng | `Containerfiles/` và `Containerfiles/patches/`; đọc build workflow trong `.github/workflows/`, sau đó trỏ image tag trong values. |
| Kiểm thử thay đổi script | `scripts/tests/`, `.pre-commit-config.yaml`, cấu hình lint; chọn test phù hợp phần sửa. |
| Dựng môi trường thử nghiệm | `testing/` hoặc script lab; đọc `env.yaml.example`, `doit.sh`, `build.yaml`, `cleanup.sh` trước khi dùng. |
| Viết tài liệu upstream | `docs/`, `mkdocs.yml`, `doc-requirements.txt`; theo `docs/mkdocs-howto.md`. |
| Ghi release note | `releasenotes/`, tham khảo `CONTRIBUTING.md`; các script `generate_release_docs.py`, `generate_product_matrix.py` hỗ trợ xuất tài liệu. |

`dev-requirements.txt` dùng cho dependencies phát triển, `.ansible-lint`/`.yamllint` cho kiểm tra cấu hình, `.github/` cho CI và mẫu issue. `SECURITY.md`, `LICENSE`, `CONTRIBUTING.md` áp dụng khi sửa/chia sẻ mã nguồn.

**Đầu ra:** thay đổi đã nằm trong file/version control và được kiểm chứng, thay vì chỉ tồn tại trong Pod đang chạy.

## 15. Ví dụ hoàn chỉnh: muốn cài Glance bằng Genestack

Giả sử bước 1–8 đã hoàn thành, bạn muốn thay các lệnh Glance thủ công trong file 05 bằng luồng Genestack:

1. Mở `docs/openstack-glance.md` và `docs/openstack-glance-ceph-store.md` hoặc tài liệu backend bạn chọn.
2. Mở `bin/install-glance.sh`: xác định chart, version file, namespace, secrets, values và post-renderer.
3. Đọc `base-helm-configs/glance/`: biết baseline hiện có trước khi copy overrides từ lab.
4. Kiểm tra `/etc/genestack/helm-chart-versions.yaml`: Glance dùng version nào?
5. Viết `/etc/genestack/helm-configs/glance/99-local-overrides.yaml`: backend, PVC/node placement/resource phù hợp với bạn. Không copy mặc định toàn bộ file lab rồi bỏ qua baseline khác nhau.
6. Kiểm tra `/etc/genestack/kustomize/glance/overlay/`: có cần manifest/patch riêng không?
7. Kiểm tra Secret mà installer gọi, DB/MQ/cache và StorageClass.
8. Render theo đúng input nếu cần xem trước; đọc manifest để xác nhận storage, placement và dependencies.
9. Chạy `/opt/genestack/bin/install-glance.sh`.
10. Kiểm tra Helm release, Pod/PVC, jobs và logs nếu có lỗi.
11. Dùng OpenStack CLI upload một image nhỏ rồi dùng image đó tạo VM để kiểm chứng đường đi.

Bạn lặp lại cách lần theo này cho Nova, Neutron, Cinder hoặc dịch vụ khác. **Điểm vào là tài liệu của dịch vụ và installer; file cấu hình cần sửa được xác định từ chính installer đó.**
