# Helm
## 1. Helm chart là bộ cài có sẵn
Ví dụ chart Nova chứa các mẫu để tạo Deployment, DaemonSet, Service, Secret… cùng cấu hình mặc định.

Nhưng bộ cài sẽ không hiểu được cấu hình của mình:
- Dùng Talos OS
- Có node gì
- Dùng local storage như nào
- Dùng mạng như thế nào ví dụ mình dùng chủ yếu OVS/OVN trực tiếp từ Kube-OVN
- Muốn đặt dữ liệu máy ảo trên ổ riêng

## 2. Folder `overrides` giữ cấu hình riêng của bạn
Hiện tại trong lab folder được tổ chức theo dạng sau:
```
~/osh-lab/overrides/
├── glance/
│   ├── 2026.1-ubuntu_noble.yaml
│   └── lab-worker-pvc.yaml
├── nova/
└── neutron/
```
- Trong đó:
  - `2026.1-ubuntu_noble.yaml`: cấu hình phù hợp bản OpenStack và image hệ điều hành đã chọn.
  - `lab-worker-pvc.yaml`: cấu hình riêng của lab bạn.

Helm không bắt buộc thư mục phải tên overrides. Đặt tên và chia folder như vậy để dễ quản lý; Helm đọc file vì bạn truyền đường dẫn bằng `-f` hoặc `--values`.

Ví dụ:
```bash
helm template glance openstack-helm/glance \
  --version '2026.1.39+dd5656a9c' \
  --namespace openstack \
  --values ~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml \
  --values ~/osh-lab/overrides/glance/lab-worker-pvc.yaml \
  > /tmp/glance-rendered.yaml
```

Helm sẽ ghép:
```
Values mặc định của chart
          ↓
Cấu hình 2026.1-ubuntu_noble.yaml
          ↓
Cấu hình lab-worker-pvc.yaml
```

Nếu hai file cấu hình cùng một key, file truyền sau được ưu tiên. Bạn cũng thấy `--set volume.size=10Gi`: đó là cách truyền một giá trị ngay trên dòng lệnh thay vì viết vào file.

- `helm template` là “xem bản thiết kế trước khi thi công”

“Helm hãy cho tôi xem nếu dùng cấu hình này thì sẽ tạo những tài nguyên gì. Lưu kết quả vào file để tôi kiểm tra.”

Sau đó dùng grep, rg, sed để tìm trong kết quả:

- `helm upgrade --install` mới là cài thật
```bash
helm upgrade --install glance openstack-helm/glance \
  --version '2026.1.39+dd5656a9c' \
  --namespace openstack \
  --values ~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml \
  --values ~/osh-lab/overrides/glance/lab-worker-pvc.yaml \
  --wait --timeout 15m
```

| Phần lệnh | Hiểu đơn giản |
|---|---|
| `glance` đầu tiên | Tên lần triển khai, gọi là **release** |
| `openstack-helm/glance` | Chart dùng làm bộ cài |
| `-f ...` | Cấu hình bạn muốn áp dụng |
| `upgrade --install` | Đã có release thì cập nhật; chưa có thì cài |
| `--wait` | Chờ các tài nguyên liên quan đạt trạng thái sẵn sàng |
| `--timeout 15m` | Giới hạn thời gian chờ |
| `--version '2026.1.39+dd5656a9c'`| dùng để chọn chính xác phiên bản Helm chart Glance mà bạn muốn cài.|

Helm ghép lệnh trên như sau:
```
Values mặc định của chart phiên bản đã chọn
                  ↓ ghi đè
       2026.1-ubuntu_noble.yaml
                  ↓ ghi đè
          lab-worker-pvc.yaml
```


Quá trình thử và sửa diễn ra:
```
Viết values
    ↓
helm template → xem kết quả
    ↓
Phát hiện chưa đúng → sửa values/chart
    ↓
helm template → kiểm tra lại
    ↓
helm upgrade --install → áp dụng
    ↓
Kiểm tra Pod và chức năng thực tế
```

- **Chart**: bộ cài có sẵn.
- **Overrides**: yêu cầu riêng của lab bạn.
- `template` → `upgrade --install`: xem bản thiết kế → áp dụng thật.

## 3. Tìm phiên bản chart và lưu vào biến
```bash
GLANCE_CHART_VERSION=$(helm search repo openstack-helm/glance --versions | awk 'NR==2 {print $2}')
printf 'Glance chart: %s\n' "$GLANCE_CHART_VERSION"
```
- `helm search repo ... --versions:` liệt kê các phiên bản chart Glance trong thông tin Helm repository trên máy.
- `|`: chuyển kết quả sang lệnh tiếp theo.
- `awk 'NR==2 {print $2}'`: lấy cột thứ hai của dòng thứ hai. Dòng đầu là tiêu đề; dòng thứ hai thường là phiên bản mới nhất trong kết quả.

### 3.1 Tải file overrides dành cho OpenStack 2026.1 và Ubuntu Noble
```bash
helm osh get-values-overrides \
  -d -p ~/osh-lab/overrides \
  -c glance 2026.1 ubuntu_noble
```

| Phần | Ý nghĩa |
|---|---|
| `helm osh get-values-overrides` | Lấy cấu hình overrides của OpenStack-Helm |
| `-d` | Tải các file overrides |
| `-p ~/osh-lab/overrides` | Thư mục lưu cấu hình |
| `-c glance` | Lấy cho chart Glance |
| `2026.1 ubuntu_noble` | Chọn cấu hình tương ứng bản OpenStack và hệ điều hành của image |

Bạn sẽ nhận được file tại:
```
~/osh-lab/overrides/glance/2026.1-ubuntu_noble.yaml
```
### 3.2 Xem values mặc định và lọc phần cần quan tâm
```bash
helm show values openstack-helm/glance \
  --version "$GLANCE_CHART_VERSION" \
  | grep -n -A12 -B3 -E '^storage:|^volume:|^volume_staging:|^labels:|^  replicas:'
```
`helm show values` đọc values mặc định của chart phiên bản đã chọn.

Sau đó `grep` chỉ hiển thị những đoạn liên quan đến:
- `storage`: loại backend lưu image.
- `volume`: cấu hình volume.
- `volume_staging`: cấu hình volume staging.
- `labels`: cấu hình nhãn, chẳng hạn chọn node.
- `replicas`: cấu hình số bản sao ở mức thụt dòng được chỉ định.

Các tùy chọn của grep:

| Tùy chọn | Ý nghĩa |
|---|---|
| `-n` | Hiện số dòng |
| `-A12` | Hiện thêm 12 dòng sau dòng khớp |
| `-B3` | Hiện thêm 3 dòng trước dòng khớp |
| `-E` | Cho phép dùng biểu thức tìm kiếm với nhiều nhánh `\|` |
| `^` trong mẫu | Khớp từ đầu dòng |

## 4. Post-render
Helm chỉ cho bạn đổi những gì tác giả chart đã mở thành biến trong values. Giả sử bạn cài chart của người khác và muốn thêm một annotation hay nodeSelector vào Deployment, nhưng chart không có biến nào cho việc đó. Lúc này có ba hướng: fork chart, sửa tay sau khi cài, hoặc dùng post-renderer.

Post-renderer là một chương trình bên ngoài mà Helm gọi sau khi render template xong và trước khi gửi lên cluster. Luồng như sau:

```
chart + values
     ↓ Helm render
YAML hoàn chỉnh ──(stdin)──► [post-renderer của bạn] ──(stdout)──► YAML đã sửa
                                                                        ↓
                                                                gửi lên K8s API
```
Helm đưa toàn bộ YAML cho chương trình đó qua stdin, chương trình sửa tùy ý rồi in kết quả ra stdout, và Helm dùng kết quả đó để cài. Nghĩa là bạn có cơ hội can thiệp vào YAML cuối cùng mà không cần đụng vào chart.

- Bạn có thể dùng nhưu sau:
```bash
helm upgrade --install myapp ./chart \
  -f values-prod.yaml \
  --post-renderer ./patch.sh
```
`patch.sh` có thể là bất cứ thứ gì đọc stdin và ghi stdout: shell script, sed, yq, Python... Cách phổ biến nhất là gọi Kustomize.

Post-renderer phải là một file thực thi (executable), không phải một chuỗi lệnh có sẵn tham số. Các bản Helm mới hơn có thêm cờ `--post-renderer-args` để truyền tham số.

> **Lưu ý** bạn sẽ rất nhầm nhưng post-render chỉ là phương thức nó chỉ là một cái cổng như usb nó không phải là USB.

Hãy hình dung như thế này một logic vô cùng phổ biến để hiểu kỹ 3 cái khái niệm này:
- Giả sử template trong chart có dòng:
```yaml
replicas: {{ .Values.replicas }}
```
Bạn đổi `replicas` trong values thì được. Nhưng giả sử template không có chỗ nào đọc `nodeSelector`, mà bạn lại muốn Pod chạy trên node SSD. Bạn viết vào values:
```yaml
nodeSelector:
  disktype: ssd
```
thì Helm lặng lẽ bỏ qua, vì không dòng template nào đọc nó. YAML cuối cùng không có nodeSelector. Values chỉ là các "biến điền vào chỗ trống" mà tác giả chart đã chừa sẵn.
- Vậy có 3 cách xử lý:

| Cách | Làm gì | Đánh đổi |
|-----|------|--------------|
| Sửa chart	`helm pull --untar`| thêm dòng nodeSelector vào template, cài từ bản sửa của bạn |	Chạy tốt, nhưng mỗi lần chart nâng version bạn phải tự gộp lại thay đổi của mình|
| `Post-renderer`	| Chart giữ nguyên, sau khi render thì một chương trình ngoài thêm nodeSelector vào YAML |	Không đụng chart, nhưng thêm một script cần bảo trì |
| Kustomize	| Chính là công cụ thường được cắm vào post-renderer ở dòng trên để làm việc vá | Có YAML thuần của riêng bạn, không có chart: Kustomize.|

## 5. Luồng của 1 Service áp dụng thông thường
- Lấy genestack làm ví dụ chính

```
chart openstack-helm  +  values (-f ...)
        ↓ helm render
   YAML hoàn chỉnh ──► kustomize.sh (post-renderer) ──► all.yaml
                                                          ↓ + resources thêm + patches
                                                  kubectl kustomize
                                                          ↓
                                                   gửi lên cluster
```
- `post-renderer` nó là một cái cầu nối file kustomize.sh vào file yaml render từ helm. 

```
BƯỚC 1: Helm
  chart Neutron (của người khác) + values (của Genestack)
        ↓
  ra một đống YAML: Deployment, Service, ConfigMap...

BƯỚC 2: Kustomize (khâu chỉnh sửa)
  nhận đống YAML đó, rồi
   • THÊM thứ chart không có (tạo database, tạo queue)
   • SỬA vài dòng chart không cho chỉnh
        ↓
  ra YAML cuối cùng

BƯỚC 3: gửi YAML cuối lên Kubernetes
```
- Nó chỉ là sợi dây nối bước 1 với bước 2. Helm vốn đi thẳng từ bước 1 sang bước 3. Cờ `--post-renderer` nói với Helm: "xong bước 1 thì đừng gửi đi vội, đưa cho script này (kustomize.sh) làm bước 2 đã".
- Helm tạo ra YAML. Post-renderer là cái cổng cho phép chen vào giữa. Kustomize là thứ được chen vào để chỉnh YAML.

## 6. Advance
- Để hình dung rõ ràng và tránh hiểu sai nhầm lẫn, ngoài dùng `post-render` như Genestack để nối Helm với Kustomize chúng ta còn nhiều cách khác.
### 6.0 Helm gọi Kustomize
- Đây là post-renderer, cái Genestack đang dùng.
### 6.1 Kustomize gọi Helm
Kustomize có trường `helmCharts` trong file `kustomization.yaml`: bạn khai tên chart, version, values, rồi Kustomize tự chạy `helm template` để lấy YAML, sau đó vá tiếp. Phải bật cờ `--enable-helm` khi chạy. 

Điểm đánh đổi cần nhớ: cách này chỉ render ra YAML rồi `kubectl apply`, nên bạn mất khái niệm release của Helm (`helm history`, `helm rollback`).

### 6.2 Tách riêng, ghép bằng tay hoặc bằng công cụ khác
```bash
helm template myapp ./chart -f values.yaml > all.yaml
# rồi kustomize build/kubectl kustomize lên all.yaml
```

Ngoài ra, các công cụ GitOps ghép hộ bạn: Flux có trường postRenderers ngay trong HelmRelease (hỗ trợ patch kiểu Kustomize), còn Argo CD hỗ trợ cả Helm lẫn Kustomize trong cùng một Application. Chi tiết cú pháp từng công cụ bạn nên đối chiếu tài liệu đúng version vì mình không kiểm chứng ở đây.

### 6.3 Ngoài Kustomize, còn gì để chỉnh YAML
Với post-renderer: nó chỉ yêu cầu "một chương trình đọc stdin, in ra stdout", nên cắm gì cũng được:
- `yq` hoặc `jq`: sửa field bằng một dòng lệnh, hợp với thay đổi nhỏ
- `sed`: thô sơ, dễ vỡ, chỉ nên dùng thay chuỗi đơn giản
- Script Python hoặc Go tự viết: khi logic phức tạp
- ytt (Carvel): ngôn ngữ template/overlay riêng, chuyên sửa YAML

Không dùng post-renderer, vẫn chỉnh được bằng cách khác:
- Sửa hoặc fork chart.
- Umbrella chart: bạn viết một chart "bọc" bên ngoài, khai chart gốc như một dependency, rồi đè values và thêm template của riêng bạn
- Chỉnh ở phía cluster sau khi gửi lên: dùng admission controller như Kyverno hoặc OPA Gatekeeper để tự động thêm hoặc sửa field khi resource được tạo (ví dụ thêm nodeSelector cho mọi Deployment). Cách này không đụng vào bước Helm hay YAML nào cả.
