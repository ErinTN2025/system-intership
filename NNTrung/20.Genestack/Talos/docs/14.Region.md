# Region
In OpenStack, a Region is defined as an independently deployed cloud infrastructure, excepting authentication (Keystone) and possibly a dashboard (Horizon or Skyline.) A Region should be able to operate autonomously from other Regions. This means that a Region has it's own API endpoints for most services. For the OpenStack CLI, this usually means a separate entry in clouds.yaml or a separate openrc file.

> **Region = một “cụm OpenStack gần như độc lập”, đặt ở một vị trí vật lý riêng, nhưng vẫn thuộc cùng một Cloud.**

Hãy tưởng tượng một công ty có cloud ở nhiều nơi:

```text
                    ONE CLOUD
                       │
          ┌────────────┴────────────┐
          │                         │
      Region Hà Nội             Region HCM
          │                         │
     ┌────┴────┐                ┌───┴────┐
     │         │                │        │
    AZ1       AZ2              AZ1      AZ2
```

Mỗi Region gần như là **một OpenStack riêng**:

```text
Region Hanoi
├── Nova
├── Neutron
├── Cinder
├── Glance
└── API endpoints

Region HCM
├── Nova
├── Neutron
├── Cinder
├── Glance
└── API endpoints
```

Điểm đặc biệt là chúng có thể **dùng chung Identity/Keystone**, nhờ đó người dùng cảm thấy mình đang dùng **một cloud duy nhất**, chứ không phải hai cloud tách biệt.

---

## 1. Cloud, Region, Availability Zone khác nhau thế nào?

Đây là phần quan trọng nhất cần nhớ.

### Cloud

Cloud là toàn bộ hệ thống mà một provider cung cấp.

Ví dụ:

```text
VNPT Cloud
```

có thể có:

```text
Cloud
├── Region Hanoi
├── Region HCM
└── Region Da Nang
```

---

### Region

Region thường đại diện cho:

> **một khu vực địa lý / một data center hoặc nhóm data center độc lập.**

Ví dụ:

```text
RegionOne = Hanoi
RegionTwo = HCM
```

Điều quan trọng:

> **Một Region phải có khả năng tiếp tục hoạt động khi Region khác bị down.**

Ví dụ HCM mất điện:

```text
Region HCM
     X

Region Hanoi
     ✓
```

Hanoi không nên phụ thuộc vào Nova, Neutron, Cinder của HCM để hoạt động.

Đó chính là câu:

> A Region should be able to operate autonomously from other Regions.

---

### Availability Zone

Availability Zone nhỏ hơn Region.

Ví dụ:

```text
Region Hanoi
├── AZ1
│   ├── compute01
│   └── compute02
│
└── AZ2
    ├── compute03
    └── compute04
```

Hiểu đơn giản:

```text
Cloud
  ↓
Region
  ↓
Availability Zone
  ↓
Compute / Storage / Network resources
```

Một cách nhớ:

> **Cloud = quốc gia  
> Region = thành phố  
> AZ = quận**

Không hoàn toàn chính xác về mặt kỹ thuật, nhưng cực kỳ dễ hình dung.

# 2. Tại sao Region lại có API endpoint riêng?

Giả sử có hai Region:

```text
Hanoi
HCM
```

Nova ở hai nơi khác nhau.

Có thể service catalog chứa:

```text
Nova Hanoi
https://nova-hn.example.com

Nova HCM
https://nova-hcm.example.com
```

Neutron cũng tương tự:

```text
Neutron Hanoi
https://neutron-hn.example.com

Neutron HCM
https://neutron-hcm.example.com
```

Do đó khi user nói:

```text
--os-region-name Hanoi
```

OpenStack client sẽ chọn endpoint của Hanoi.

Ví dụ logic:

```text
User
 ↓
Keystone
 ↓
Service Catalog
 ↓
Region = Hanoi
 ↓
Nova Hanoi
Neutron Hanoi
Cinder Hanoi
Glance Hanoi
```

Đây cũng là lý do tài liệu nói mỗi Region thường có:

```text
clouds.yaml riêng
```

hoặc:

```text
openrc riêng
```

Không phải vì bắt buộc, mà vì mỗi Region có endpoint khác nhau.

# 3. Generic DNS và Geo-IP để làm gì?

Ví dụ thay vì user phải nhớ:

```text
hanoi.cloud.company.com
hcm.cloud.company.com
```

provider có thể cho user truy cập:

```text
cloud.company.com
```

DNS sẽ xác định user đang gần nơi nào hơn.

Ví dụ:

```text
User ở Hanoi
       │
       ↓
cloud.company.com
       │
     GeoDNS
       │
       ↓
hanoi.cloud.company.com
```

User ở Singapore:

```text
cloud.company.com
       │
       ↓
apac.cloud.company.com
```

Đây chủ yếu là **cách điều hướng user tới Region phù hợp**.

# 4. Keystone — cái gắn các Region thành một Cloud

Đây là service quan trọng nhất trong multi-region.

Thông thường:

```text
             Keystone
                │
        ┌───────┴───────┐
        │               │
   Region Hanoi      Region HCM
```

Keystone quản lý:

```text
User
Project
Role
Authentication
Authorization
Service Catalog
```

Ví dụ user:

```text
username: trung
project: admin
```

đăng nhập một lần.

Keystone biết:

```text
Nova Hanoi → endpoint A
Nova HCM   → endpoint B

Neutron Hanoi → endpoint C
Neutron HCM   → endpoint D
```

Vậy nên:

> **Keystone chung chính là thứ khiến nhiều Region được nhìn nhận như một Cloud.**

Nếu mỗi Region có Keystone hoàn toàn riêng:

```text
Keystone Hanoi
Keystone HCM
```

thì chúng gần giống:

```text
2 OpenStack clouds độc lập
```

hơn là:

```text
1 Cloud có 2 Regions
```

# 5. Keystone Federation là gì?

Không nhất thiết mọi Region phải gọi về **một Keystone server duy nhất**.

Có thể:

```text
Global Identity
       │
       ├── Keystone Hanoi
       │
       └── Keystone HCM
```

Các Keystone có thể sử dụng federation.

Ngoài ra identity thật sự của doanh nghiệp thường được lưu trong:

```text
LDAP
Active Directory
OIDC
SAML
```

Ví dụ:

```text
Employee
   ↓
LDAP / AD
   ↓
Keystone
   ↓
OpenStack
```

Keystone không nhất thiết là nơi lưu toàn bộ user.

# 7. Nova — dễ hiểu nhất trong Multi-Region

Nova nên **tách riêng theo Region**.

Ví dụ:

```text
Region Hanoi
├── nova-api
├── nova-scheduler
├── nova-conductor
└── compute nodes Hanoi

Region HCM
├── nova-api
├── nova-scheduler
├── nova-conductor
└── compute nodes HCM
```

VM của Hanoi thuộc Hanoi.

VM của HCM thuộc HCM.

Không nên:

```text
Nova Hanoi
    │
    └── điều khiển compute ở HCM
```

vì khi WAN giữa hai nơi chết thì Region sẽ không còn autonomous.

---

## Di chuyển VM giữa Region

Không giống live migration trong cùng cluster.

Thông thường:

```text
VM Hanoi
   ↓
export / image / backup
   ↓
transfer
   ↓
import
   ↓
VM HCM
```

Hoặc cách phổ biến hơn:

> deploy workload ở cả hai Region ngay từ đầu.

Ví dụ:

```text
          DNS / Load Balancer
               │
       ┌───────┴────────┐
       │                │
     Hanoi             HCM
       │                │
     App VM           App VM
```

Nếu Hanoi chết:

```text
traffic → HCM
```

Đây mới là kiến trúc multi-region HA thực tế.

# 8. Neutron — tại sao không tạo một network kéo xuyên 2 Region?

Đây là đoạn rất đáng nhớ.

Giả sử muốn:

```text
Network 10.0.0.0/24
```

tồn tại cả:

```text
Hanoi
HCM
```

thì phát sinh câu hỏi:

```text
Ai sở hữu network này?
```

Hanoi?

```text
Neutron Hanoi
```

hay HCM?

```text
Neutron HCM
```

Nếu cả hai cùng sở hữu:

```text
Neutron Hanoi ←→ sync ←→ Neutron HCM
```

thì sao nếu đường WAN bị đứt?

```text
Hanoi       X       HCM
```

State sẽ diverge.

Ví dụ:

```text
Hanoi:
network = ACTIVE

HCM:
network = DOWN
```

Ai đúng?

Đây là lý do tài liệu nói:

> Đừng cố biến Neutron thành một distributed database xuyên Region.

Thay vào đó:

```text
Neutron Hanoi        Neutron HCM
     │                    │
 Network A            Network B
     │                    │
     └────── VPN ─────────┘
```

Mỗi Region sở hữu network riêng.

VPN chỉ làm nhiệm vụ **kết nối hai network**.

Đây là thiết kế rất sạch.

---

# 9. Vì sao VPN phù hợp?

VPN không thuộc hoàn toàn về một Region.

Nó chỉ:

```text
Network Hanoi
     │
     │ encrypted tunnel
     │
Network HCM
```

Ví dụ:

```text
Hanoi LAN
10.10.0.0/16
     │
 Gateway
     ║
 WireGuard VPN
     ║
 Gateway
     │
HCM LAN
10.20.0.0/16
```

VM Hanoi:

```text
10.10.1.10
```

có thể nói chuyện với:

```text
10.20.1.20
```

ở HCM.

Hai Neutron vẫn độc lập.

Đây chính là điều ta muốn.

# 10. Vì sao tài liệu không khuyến nghị Neutron VPNaaS?

VPNaaS chủ yếu được thiết kế cho các use case VPN cụ thể trong Neutron.

Còn kết nối Region-to-Region thường phù hợp hơn với:

```text
site-to-site VPN
```

hoặc:

```text
point-to-point VPN
```

như:

```text
WireGuard
IPSec
Tailscale
```

Ý tưởng là:

```text
Region A Gateway
       ║
       ║ VPN
       ║
Region B Gateway
```

# 11. Cinder — tại sao nên nằm trong Region?

Cinder quản lý:

```text
Block Storage
Volumes
Snapshots
Attachments
```

Ví dụ:

```text
Region Hanoi
VM
 │
 └── volume Hanoi
```

Volume nên gần VM về mặt vật lý.

Không nên:

```text
VM Hanoi
   │
   │ WAN
   ↓
Cinder HCM
```

vì:

- latency cao
- WAN failure
- performance kém
- Region không autonomous

Nên:

```text
Region Hanoi
Nova Hanoi
Cinder Hanoi

Region HCM
Nova HCM
Cinder HCM
```

# 12. Cinder replication khó ở đâu?

Giả sử volume Hanoi:

```text
volume-001
100 GB
```

Bạn muốn replicate sang HCM.

Không chỉ cần copy data:

```text
Hanoi Storage
     │
     └──── replicate ────→ HCM Storage
```

mà còn phải replicate **metadata/state**.

Ví dụ Hanoi biết:

```text
volume ID: abc
status: in-use
attached_to: VM001
size: 100GB
```

HCM cũng phải hiểu:

```text
abc
```

là **chính volume đó**, chứ không phải volume khác.

Và state phải consistent.

Ví dụ:

```text
Hanoi:
volume abc = attached

HCM:
volume abc = available
```

thì sẽ rất nguy hiểm.

Do đó cross-region block storage replication cực kỳ phức tạp.

---

# 13. Glance — service đặc biệt hơn

Glance quản lý image.

Ví dụ:

```text
Ubuntu 24.04
Rocky Linux 9
Windows Server
Cirros
```

Khác Cinder ở chỗ image thường:

```text
read-mostly
```

nên dễ replicate hơn volume.

Do vậy có hai kiến trúc.

---

## Cách 1 — Glance riêng từng Region

```text
Region Hanoi
└── Glance Hanoi

Region HCM
└── Glance HCM
```

Sau đó replicate:

```text
Glance Hanoi
      │
      ↓
glance-replicator
      │
      ↓
Glance HCM
```

Ví dụ:

```text
Ubuntu-24.04
```

được copy sang cả hai Region.

# 14. Shared Glance + distributed backend

Một thiết kế khác:

```text
                 Glance API
                     │
              replicated storage
                 /        \
                /          \
           Hanoi storage   HCM storage
```

User nhìn thấy:

```text
Ubuntu-24.04
```

như một image duy nhất.

Nhưng dữ liệu image thực tế có bản copy local ở từng Region.

Ví dụ:

```text
                Ubuntu image
                     │
         ┌───────────┴───────────┐
         │                       │
      Hanoi copy              HCM copy
```

Khi VM Hanoi boot:

```text
Nova Hanoi
   ↓
Glance
   ↓
Hanoi storage
```

Khi VM HCM boot:

```text
Nova HCM
   ↓
Glance
   ↓
HCM storage
```

Không phải kéo hàng chục GB qua WAN.

Đây là ý nghĩa của:

> shared Glance service with distributed backends.


Note

# OpenStack Multi-Region

## 1. Khái niệm

Một **Cloud** có thể chứa nhiều **Region**.

```text
Cloud
├── Region A
│   ├── AZ1
│   └── AZ2
└── Region B
    ├── AZ1
    └── AZ2
```

Region thường đại diện cho một khu vực vật lý hoặc data center độc lập.

Điểm quan trọng nhất:

> Một Region phải có khả năng hoạt động độc lập với các Region khác.

Nếu Region A gặp sự cố, Region B vẫn phải có thể vận hành Nova, Neutron, Cinder và các workload của mình.

---

## 2. Region khác Availability Zone

Thứ tự phân cấp:

```text
Cloud
  ↓
Region
  ↓
Availability Zone
  ↓
Compute / Storage / Network resources
```

Có thể hình dung:

- Cloud = toàn bộ hạ tầng cloud của provider.
- Region = một khu vực địa lý hoặc cụm data center.
- Availability Zone = một miền failure nhỏ hơn bên trong Region.

---

## 3. API Endpoint

Mỗi Region thường có endpoint riêng cho các service.

Ví dụ:

```text
Nova Hanoi → nova-hn.example.com
Nova HCM   → nova-hcm.example.com

Neutron Hanoi → neutron-hn.example.com
Neutron HCM   → neutron-hcm.example.com
```

Khi user chọn:

```text
--os-region-name Hanoi
```

OpenStack client sẽ sử dụng endpoint tương ứng với Region Hanoi.

---

## 4. Keystone

Keystone là thành phần có thể được dùng chung giữa các Region.

Kiến trúc:

```text
             Keystone
                │
        ┌───────┴───────┐
        │               │
   Region Hanoi      Region HCM
```

Keystone cung cấp:

- Authentication
- Authorization
- User
- Project
- Role
- Service Catalog

Việc dùng chung hoặc federation Keystone giúp nhiều Region được nhìn nhận như một Cloud duy nhất.

Quy tắc dễ nhớ:

```text
Keystone = Cloud-wide
```

---

## 5. Horizon / Skyline

Horizon và Skyline là giao diện web của OpenStack.

Có thể triển khai:

```text
Horizon Hanoi → Region Hanoi
Horizon HCM   → Region HCM
```

hoặc sử dụng landing page để user lựa chọn Region.

OpenStack Dashboard không cung cấp hoàn chỉnh một giao diện quản trị multi-region duy nhất. Nếu muốn quản lý nhiều Region từ một giao diện chung có thể sử dụng Cloud Management Platform như ManageIQ.

---

## 6. Nova

Nova nên được triển khai độc lập trong từng Region.

```text
Region Hanoi
└── Nova Hanoi
    └── Compute Hanoi

Region HCM
└── Nova HCM
    └── Compute HCM
```

VM thuộc Region nào thì được quản lý bởi Nova của Region đó.

Thông thường không live-migrate VM trực tiếp giữa các Region.

Cách phổ biến hơn:

```text
VM Region A
    ↓
export / backup / image
    ↓
transfer
    ↓
Region B
    ↓
deploy VM mới
```

Trong hệ thống HA, workload thường được triển khai đồng thời ở nhiều Region.

---

## 7. Neutron

Neutron nên độc lập theo từng Region.

Không nên tạo một Neutron network có state dùng chung xuyên nhiều Region vì sẽ phát sinh vấn đề ownership và state synchronization.

Ví dụ không nên:

```text
Neutron Hanoi
      ↕
shared network state
      ↕
Neutron HCM
```

Nếu WAN bị lỗi, state có thể không còn đồng bộ.

Thiết kế phù hợp hơn:

```text
Neutron Hanoi          Neutron HCM
     │                      │
Network Hanoi            Network HCM
     │                      │
     └─────── VPN ──────────┘
```

Mỗi Region quản lý network của mình, còn VPN đảm nhiệm kết nối giữa các Region.

---

## 8. Inter-Region Network

Kết nối mạng giữa các Region thường sử dụng:

- Site-to-site VPN
- WireGuard
- IPSec
- Tailscale
- Dedicated WAN

Ví dụ:

```text
Hanoi
10.10.0.0/16
     │
 Gateway
     ║
   VPN
     ║
 Gateway
     │
HCM
10.20.0.0/16
```

Nhờ đó hai Region có thể giao tiếp nhưng vẫn giữ quyền quản lý network độc lập.

---

## 9. Cinder

Cinder nên nằm trong từng Region.

```text
Region Hanoi
├── Nova Hanoi
└── Cinder Hanoi

Region HCM
├── Nova HCM
└── Cinder HCM
```

Volume nên nằm gần compute sử dụng nó để tránh:

- WAN latency
- network failure
- performance thấp
- dependency giữa Region

Cross-region volume replication phức tạp vì không chỉ cần replicate dữ liệu mà còn phải đồng bộ metadata và state của volume.

Ví dụ cần đồng bộ:

```text
volume ID
size
status
attachment
backend
metadata
```

---

## 10. Glance

Glance linh hoạt hơn các service khác.

### Phương án 1: Glance riêng từng Region

```text
Glance Hanoi
Glance HCM
```

Image được replicate giữa các Glance.

### Phương án 2: Shared Glance + replicated backend

```text
                 Glance
                   │
         replicated storage
             /          \
        Hanoi copy     HCM copy
```

User nhìn thấy cùng một image nhưng mỗi Region có dữ liệu image ở local storage của mình.

Điều này giúp VM boot nhanh và tránh phải truyền image lớn qua WAN.

## 11. Quy tắc ghi nhớ

```text
Identity → GLOBAL
Compute  → LOCAL
Network  → LOCAL
Volume   → LOCAL
Image    → MAYBE GLOBAL
```

Tương ứng:

```text
Keystone → Cloud-wide

Nova     → per Region
Neutron  → per Region
Cinder   → per Region

Glance   → per Region hoặc replicated/shared
```

## 12. Kiến trúc tổng thể

```text
                     User
                       │
                       ↓
                 Global Keystone
                       │
               Service Catalog
                       │
           ┌───────────┴───────────┐
           │                       │
      Region Hanoi             Region HCM
           │                       │
    ┌──────┼───────┐        ┌──────┼───────┐
    │      │       │        │      │       │
   Nova Neutron  Cinder    Nova Neutron  Cinder
    │      │       │        │      │       │
 Compute Network Storage Compute Network Storage
           │                       │
           └──────── VPN ──────────┘
                       │
                    Glance
               replicated images
```

Mục tiêu quan trọng nhất của thiết kế Multi-Region là:

> Nếu một Region bị mất kết nối hoặc gặp sự cố, các Region còn lại vẫn phải có khả năng hoạt động độc lập.

Đó là nguyên tắc **Region autonomy**.

Một câu duy nhất để bạn nhớ toàn bộ đoạn tài liệu này là:

**“Keystone nối các Region thành một Cloud; còn Nova, Neutron và Cinder phải tự sống được trong từng Region.”**
