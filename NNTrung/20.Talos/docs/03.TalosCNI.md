# Tải và cài đặt KubeOVN

Bạn không thể cài Talos CNI Kube OVN: theo cách bình thường mà bắt buộc phải qua Helm

Talos có root filesystem read-only. Manifest mặc định của Kube-OVN mount hostPath vào `/etc/origin/ovn`, `/etc/openvswitch`, `/var/run/openvswitch`, `/var/log/ovn`... và cố tạo hoặc chown các thư mục đó. Việc này thất bại trên Talos nên container init không tạo được.

---

## 1. DNS không resolve được `registry-1.docker.io`

```
dial tcp: lookup registry-1.docker.io on 127.0.0.53:53: server misbehaving
```
Node không pull được image `kubeovn/kube-ovn`.

**Kiểm tra:**
```bash
resolvectl status
sudo apt install -y dnsutils
nslookup registry-1.docker.io 192.168.207.2
nslookup registry-1.docker.io 1.1.1.1
nslookup registry-1.docker.io 8.8.8.8
```

**Kết quả:** Cả 3 DNS server đều resolve được ⇒ mạng/DNS ổn, lỗi trước đó chỉ là tạm thời hoặc do resolver nội bộ (`127.0.0.53`) trên node Talos lỗi. Sau khi retry, image pull thành công.

## 2. Init container `hostpath-init` lỗi: root filesystem read-only
- Trước tiên ưu tiên check lỗi trước:
```bash
kubectl -n kube-system describe pod ovs-ovn-24rwj | tail -30
kubectl -n kube-system describe pod ovn-central-6c57bbcb94-tgf64 | tail -30
```
- Pod name là tên các pod initcontainererror khi bạn `kubectl get po -A -w`

```
failed to mkdir "/etc/origin/openvswitch": mkdir /etc/origin: read-only file system
failed to mkdir "/etc/origin/ovn": mkdir /etc/origin: read-only file system
```
Pod `ovs-ovn` và `ovn-central` kẹt ở `Init:CreateContainerError`.

**Nguyên nhân:** Manifest/cài đặt Kube-OVN mặc định (theo hướng dẫn cài trên web chung, không phải trang riêng cho Talos) mount hostPath vào `/etc/origin/...`. Trên Talos, `/etc` thuộc root filesystem **read-only**, nên kubelet không tạo được thư mục.

**Cách sửa:** Kube-OVN có trang cài riêng cho Talos, dùng Helm với các giá trị đổi đường dẫn sang nơi ghi được:

```bash
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
helm version
```

- Gỡ bản OVN đang lỗi:
```bash
kubectl -n kube-system get deploy,ds,svc,sa,cm -o name | grep -E 'ovn|ovs'
kubectl get clusterrole,clusterrolebinding,crd -o name | grep -E 'ovn|ovs|kubeovn'
```
- Nếu danh sách đúng toàn đồ OVN thì xóa:
```bash
kubectl -n kube-system get deploy,ds,svc,sa,cm -o name | grep -E 'ovn|ovs' \
  | xargs kubectl -n kube-system delete --ignore-not-found

kubectl get clusterrole,clusterrolebinding,crd -o name | grep -E 'ovn|ovs|kubeovn' \
  | xargs kubectl delete --ignore-not-found
```
- Check:
```bash
kubectl -n kube-system get pods
```
- Liệt kê mọi thứ còn sót lại:
- Resource trong ns `kube-system`
```bash
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n1 kubectl -n kube-system get --ignore-not-found -o name 2>/dev/null \
  | grep -Ei 'ovn|ovs|ipsec' | grep -Ev '^event' | tee /tmp/ns-leftover.txt
```
- Resource cluster-scoped
```bash
kubectl api-resources --verbs=list --namespaced=false -o name \
  | xargs -n1 kubectl get --ignore-not-found -o name 2>/dev/null \
  | grep -Ei 'ovn|ovs|kubeovn' | tee /tmp/cluster-leftover.txt
```
- Chắc toàn đồ OVN, Xóa hết sạch luôn
```bash
xargs -a /tmp/ns-leftover.txt kubectl -n kube-system delete --ignore-not-found
xargs -a /tmp/cluster-leftover.txt kubectl delete --ignore-not-found
```

```bash
helm repo add kubeovn https://kubeovn.github.io/kube-ovn/
helm repo update

helm install kube-ovn kubeovn/kube-ovn \
  -n kube-system \
  --version 1.16.7 \
  --set OVN_DIR=/var/lib/ovn \
  --set OPENVSWITCH_DIR=/var/lib/openvswitch \
  --set DISABLE_MODULES_MANAGEMENT=true \
  --set cni_conf.MOUNT_LOCAL_BIN_DIR=false \
  --set replicaCount=1
```
- `OVN_DIR` / `OPENVSWITCH_DIR`: đổi từ `/etc/origin/...` sang `/var/lib/...` (ghi được trên Talos).
- `DISABLE_MODULES_MANAGEMENT=true`: không để pod tự mount/quản lý kernel module của host.
- `cni_conf.MOUNT_LOCAL_BIN_DIR=false`: không mount thư mục bin của host.
- `replicaCount=1`: vì cluster chỉ có 1 control plane (mặc định chart là 3, dư ra sẽ `Pending`).


**Chưa có Helm?** Cài trực tiếp trên bastion:
```bash
curl -fsSL https://raw.githubusercontent.com/helm/helm/main/scripts/get-helm-3 | bash
# hoặc: sudo snap install helm --classic
```

**Nếu muốn Upgrade sau này**:
```bash
helm upgrade kube-ovn kubeovn/kube-ovn -n kube-system \
  --version 1.16.7 \
  --reuse-values \
  --set OVN_DIR=/var/lib/ovn \
  --set OPENVSWITCH_DIR=/var/lib/openvswitch \
  --set DISABLE_MODULES_MANAGEMENT=true \
  --set cni_conf.MOUNT_LOCAL_BIN_DIR=false \
  --set replicaCount=2
```

## 3. Helm không cài được vì resource cũ còn sót lại

**Triệu chứng:**
```
Error: INSTALLATION FAILED: Unable to continue with install: Role "secret-reader-ovn-ipsec" in namespace "kube-system" exists and cannot be imported into the current release: invalid ownership metadata...
```

**Nguyên nhân:** Bản Kube-OVN cài trước đó (bằng `kubectl apply` / `install.sh`, không qua Helm) để lại các resource (Role, RoleBinding...) không có label/annotation của Helm. Helm từ chối "nhận" các resource không do nó tạo.

**Cách gỡ sạch trước khi cài lại bằng Helm:**
```bash
# Liệt kê resource còn sót trong namespace kube-system
kubectl api-resources --verbs=list --namespaced -o name \
  | xargs -n1 kubectl -n kube-system get --ignore-not-found -o name 2>/dev/null \
  | grep -Ei 'ovn|ovs|ipsec' | grep -Ev '^event' | tee /tmp/ns-leftover.txt

# Liệt kê resource cluster-scoped (CRD, ClusterRole...)
kubectl api-resources --verbs=list --namespaced=false -o name \
  | xargs -n1 kubectl get --ignore-not-found -o name 2>/dev/null \
  | grep -Ei 'ovn|ovs|kubeovn' | tee /tmp/cluster-leftover.txt

# Xóa
xargs -a /tmp/ns-leftover.txt kubectl -n kube-system delete --ignore-not-found
xargs -a /tmp/cluster-leftover.txt kubectl delete --ignore-not-found

# Kiểm tra không còn release Helm dở dang
helm list -A -a
```
Sau khi sạch, chạy lại `helm install` như mục 2. Nếu Helm báo tiếp resource khác chưa được import, xóa đúng resource đó rồi cài lại.

## 4. `kube-ovn-cni` báo readiness probe thất bại

**Triệu chứng:**
```
Readiness probe failed: Get "http://192.168.207.137:10665/readyz": dial tcp 192.168.207.137:10665: connect: connection refused
```
`ovs-ovn` và `kube-ovn-cni` kẹt ở `0/1 Running` lâu, node vẫn `NotReady`, CoreDNS vẫn `Pending`.

**Kiểm tra kernel module (giả thuyết ban đầu, sau xác nhận KHÔNG phải nguyên nhân):**
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 dmesg | tail -50
```
Dmesg cho thấy `ovs-system`, `br-int`, `mirror0`, `ovn0` đã được tạo thành công ⇒ OVS/kernel module hoạt động bình thường trên Talos, không phải nguyên nhân.

**Nguyên nhân thật:** Sau khi `ovn0` (interface join subnet của Kube-OVN, dải `100.64.0.0/16`) xuất hiện, Talos tự chọn nhầm IP `100.64.0.2` để quảng bá cho **etcd peer URL**, gây xáo trộn và kubelet bị restart trong lúc CNI đang khởi động.

## 5. Etcd quảng bá sai peer URL (dùng IP của `ovn0` thay vì IP thật)

**Triệu chứng:**
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 etcd members
```
```
PEER URLS: https://100.64.0.2:2380     (SAI, phải là IP thật 192.168.207.137)
CLIENT URLS: https://192.168.207.137:2379   (đúng)
```

**Lưu ý:** Có 2 IP trên node là **bình thường**:
- `192.168.207.137` — IP thật trên `ens33`, IP tĩnh đã đặt.
- `100.64.0.2` — IP của interface `ovn0` do Kube-OVN tự tạo (join subnet nội bộ).

Vấn đề không phải là có 2 IP, mà là Talos chọn nhầm IP nào để quảng bá.

**Cách sửa:** Ghim rõ subnet cho node IP và cho etcd trong `controlplane.yaml` (gộp vào các mục `machine:` / `cluster:` đã có sẵn, không tạo mục trùng):
```yaml
machine:
  kubelet:
    nodeIP:
      validSubnets:
        - 192.168.207.0/24
cluster:
  etcd:
    advertisedSubnets:
      - 192.168.207.0/24
```
Áp dụng:
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 apply-config --file controlplane.yaml
```
Kubelet/etcd sẽ restart, `kubectl` có thể mất kết nối tạm 1-2 phút — bình thường, cứ đợi.

**Kiểm tra lại:**
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 etcd members
kubectl get nodes -o wide
```
`PEER URLS` phải về `https://192.168.207.137:2380`.

## 6. Sau khi tắt/mở lại máy: `time is not in sync yet`

**Triệu chứng:**
```bash
talosctl bootstrap
# error executing bootstrap: 1 error occurred:
#   * 192.168.207.137: rpc error: code = FailedPrecondition desc = time is not in sync yet
```

> ⚠️ **CẢNH BÁO QUAN TRỌNG:** Không chạy lại `talosctl bootstrap` trên cluster đã tồn tại. Lệnh này chỉ dùng **đúng 1 lần** để khởi tạo etcd lúc dựng cluster mới. Cluster đã bootstrap rồi và đã có dữ liệu — chạy lại có thể tạo etcd mới đè lên, mất toàn bộ state cũ (OVN, CoreDNS, config...).

**Lỗi liên quan khi dùng `--insecure`:**
```bash
talosctl apply-config --insecure --nodes 192.168.207.137 --file controlplane.yaml
# error: rpc error: code = Unavailable desc = ... "tls: certificate required"
```
Đây thực ra là **tin tốt**: nó nghĩa là node **không** ở chế độ maintenance/mất config — vẫn đang chạy config cũ với chứng chỉ cũ, nên từ chối kết nối insecure. Chỉ cần dùng kết nối bình thường (không `--insecure`):
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 apply-config --file controlplane.yaml
```

**Nguyên nhân "time is not in sync":** Đồng hồ VM bị lệch sau khi tắt/mở máy (thường gặp với máy ảo). Talos chủ động chặn `etcd`, `kubelet`, `trustd` khởi động cho tới khi NTP đồng bộ xong, để tránh etcd hỏng dữ liệu vì lệch giờ. Đây là hành vi **bảo vệ bình thường**, không phải lỗi nghiêm trọng — miễn là nó tự hết sau khi đồng bộ xong.

**Cách kiểm tra:**
```bash
talosctl -e 192.168.207.137 -n 192.168.207.137 get timesyncstatus
talosctl -e 192.168.207.137 -n 192.168.207.137 service
talosctl -e 192.168.207.137 -n 192.168.207.137 get timeserverstatus
```

**Nếu bị kẹt lâu ở "Waiting for time sync"** (NTP server không phản hồi được — có thể do mạng chặn UDP 123, giống kiểu 8.8.8.8 từng bị timeout DNS): đổi NTP server trong `controlplane.yaml`:
```yaml
machine:
  time:
    servers:
      - 192.168.207.2
      - pool.ntp.org
```
Áp dụng lại bằng `apply-config` (không `--insecure`, không `bootstrap`).

## Bài học chung

1. **Luôn dùng trang cài đặt riêng cho từng hệ điều hành/distro** nếu nhà cung cấp phần mềm có cung cấp (Kube-OVN có trang riêng cho Talos) — tránh lỗi do giả định filesystem ghi được như trên Ubuntu/Debian thường.
2. **Đừng trộn cách cài** (`kubectl apply` / `install.sh` rồi sau đó Helm) — dọn sạch resource cũ trước khi đổi phương thức cài.
3. **Đọc kỹ `Events` trong `kubectl describe pod`** trước khi đoán nguyên nhân — tránh sửa nhầm hướng (ví dụ từng nghi kernel module nhưng thực ra là etcd peer URL).
4. **Không có node IP cố định = rủi ro với etcd/kubelet trên Talos** khi cài CNI overlay (Kube-OVN, Cilium...) vì các CNI này tạo thêm interface/IP nội bộ (`ovn0`, `cni0`...). Luôn ghim `machine.kubelet.nodeIP.validSubnets` và `cluster.etcd.advertisedSubnets` về đúng subnet mạng thật.
5. **`talosctl bootstrap` là hành động một lần, không phải lệnh khởi động lại cluster.** Nếu cluster đã chạy, không cần và không nên gọi lại.
6. **Sau khi tắt/mở máy ảo, luôn kiểm tra time sync trước** khi nghi ngờ các lỗi khác — nhiều service Talos (etcd, kubelet, trustd) chủ động chờ NTP xong mới chạy.
