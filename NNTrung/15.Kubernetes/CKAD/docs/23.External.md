# AccountService, Role, Rolebinding
## 1. Service Account
- "Danh tính" cho ứng dụng
- Khi một người dùng (admin, dev) tương tác với K8s qua `kubectl`, họ dùng User Account (thường gắn với cert, OIDC, token...). Khi một người dùng (admin, dev) tương tác với K8s qua kubectl, họ dùng User Account (thường gắn với cert, OIDC, token...).
- User Account dành cho con người, Service Account dành cho process/Pod.

Đặc điểm:
- Là một resource namespaced (`kind: ServiceAccount`)
- Mỗi namespace có sẵn một SA mặc định tên `default`
- Nếu Pod không khai báo `serviceAccountName`, nó sẽ tự dùng `default`
- K8s tự động mount token của SA vào Pod (dạng file JWT) tại:
```
  /var/run/secrets/kubernetes.io/serviceaccount/token
```
- Pod dùng token này để xác thực (authenticate) khi gọi API server.

- Ví dụ:
```yaml
apiVersion: v1
kind: ServiceAccount
metadata:
  name: app-sa
  namespace: default
```
- Sau đó Pod có thể sử dụng: spec: `serviceAccountName: app-sa`

## 2. Role: 

Định nghĩa quyền được phép làm gì, có phạm vi là trong 1 namespace.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: pod-reader
  namespace: default
rules:
  - apiGroups: [""]           # "" nghĩa là core API group
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
```

## 2. RBAC (Role-Based Access Control)
- Nó là quyền hạn dùng để trả lời câu hỏi Ai được làm gì, ở đâu, Nó gồm có 4 loại chính:

| Object |	Phạm vi |	Ý nghĩa|
|--------|----------|---------|
| Role | 	1 namespace	 | Tập hợp các quyền (verbs) trên các resource |
| RoleBinding |	1 namespace |	Gán Role đó cho ai (user/group/SA)|
| ClusterRole| 	Toàn cluster| 	Giống Role nhưng áp dụng được cả cluster-scoped resource (Node, PV...) hoặc dùng chung nhiều namespace|
| ClusterRoleBinding |	Toàn cluster |	Gán ClusterRole cho ai, áp dụng toàn cluster|


## 2. RoleBinding 
Kết hợp giữa ServiceAccount với role. Gắn "ai" với "được làm gì". Hãy tưởng tượng bạn tạo 1 ServiceAccount và 1 Role nhưng chúng không thể tự động liên kết với nhau mà bạn phải binding ở giữa.
  - Lưu ý: Role Binding không chỉ dành cho mỗi Service Accounts mà còn có thể cho User, Group, nói chung tất cả những thứ mà role có thể bind được.
- Ví dụ:
```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: pod-reader-binding
  namespace: default
subjects:
  - kind: ServiceAccount
    name: my-app-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```
## 3. ClusterRole 
Permission có phạm vi cluster-wide hoặc có thể được bind vào namespace cụ thể. Ví dụ xem quyền Nodes, thì phải dùng ClusterRole vì role chỉ có giới hạn Namespace.
## 4. ClusterRoleBinding 
Gán subject vào ClusterRole

# Securitycontext
## 1. Khái niệm
- `SecurityContext`: trong Kubernetes là một phần rất quan trọng. Nó dùng để kiểm soát cách container chạy về mặt security: chạy bằng user nào, group nào, có được dùng root không, Linux capabilities nào được phép, filesystem có read-only không, v.v.
  - `securityContext` = quy định container này được phép chạy như thế nào về mặt bảo mật.

## 2. Cấu trúc YAML
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: security-demo
spec:
  containers:
  - name: app
    image: nginx
    securityContext:
      runAsUser: 1000
      runAsGroup: 1000
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
```
- chạy bằng UID `1000`
- chạy bằng GID `1000`
- không được privilege escalation
- root filesystem ở chế độ read-only

## 3. Lưu ý khi dùng
- `securityContext` có thể nằm ở: `spec` hoặc bên trong `containers`
- Nếu container-level và Pod-level cùng khai báo một thuộc tính thì container-level sẽ override giá trị Pod-level cho thuộc tính đó.
- Ví dụ:
```yaml
spec:
  securityContext:
    runAsUser: 1000

  containers:
  - name: app
    image: nginx
    securityContext:
      runAsUser: 2000
```
- Pod default: runAsUser = 1000 meanwhile app Container: runAsUser = 2000
- `fsGroup`: liên quan đến quyền truy cập filesystem/volume.
- `allowPrivilegeEscalation`: Nó kiểm soát việc process có thể tăng privilege cao hơn privilege hiện tại hay không.
- `readOnlyRootFilesystem`: cho phép đọc root file system của container hay không.
- `privilegde`: Cho container chạy ở privileged mode. Đây là quyền rất mạnh và thường không nên bật nếu không thực sự cần.
- `Linux capabilites`: Linux có một cơ chế gọi là capabilities để chia nhỏ quyền root. Ví dụ:
```yaml
securityContext:
  capabilities:
    drop:
    - ALL
    add:
    - NET_BIND_SERVICE
```
- Remove toàn bộ Linux capabilities mà container đang có. Chỉ add quyền thực sự cần.

## Cần phân biệt
- ServiceAccount + RBAC: quyết định Container được phép làm gì trên Kubernetes API
- securityContext: quyết định bên trong container được chạy như thế nào trên Linux/container runtime.
