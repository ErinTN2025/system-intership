# API deprecation: phát hiện và sửa manifest dùng API cũ

## Lý thuyết cốt lõi

`apiVersion` không phải phiên bản của Kubernetes Cluster, mà là phiên bản của API dùng để giao tiếp với một loại tài nguyên.

2 dòng đầu khi config resources:
```yaml
apiVersion: apps/v1
kind: Deployment
```
- `apiVersion: apps/v1`: Tôi đang sử dụng phiên bản v1 của nhóm API apps.
- `kind: Deployment`: Tôi muốn làm việc với loại tài nguyên Deployment.

Kubernetes API Server sẽ dựa vào thông tin này để biết cách giải mã, kiểm tra và xử lý object.

Một Kubernetes Cluster có thể đồng thời phục vụ nhiều API group/version:

| apiVersion |	kind |	Ý nghĩa|
|----------|-----------|-----------|
| `v1` |	Pod |	Core API group, phiên bản v1|
| `apps/v1` |	Deployment |	Nhóm apps, phiên bản v1 |
| `batch/v1` |	Job	Nhóm batch, phiên bản v1 |
| `networking.k8s.io/v1` |	Ingress	Nhóm networking, phiên bản v1|
| `monitoring.coreos.com/v1` |	ServiceMonitor|	API do CRD mở rộng|

## Lab: chuyển Deployment `extensions/v1beta1` sang `apps/v1`

Yêu cầu: cluster lab hiện đại và `kubectl`. File cũ sau cố ý không hợp lệ với cluster đã bỏ API cũ; **đừng apply file này**.

- Check cluster hiện tại hỗ trợ API Version nào:
```bash
kubectl api-versions
```
Lệnh này liệt kê những API group/version đang được API Server phục vụ.
- Check resources:
```bash
kubectl api-resources
```
Muốn xem riêng networking:
```bash
kubectl api-resources \
  --api-group=networking.k8s.io
```
Muốn kiểm tra schema:
```bash
kubectl explain ingress --api-version=networking.k8s.io/v1
```

```bash
mkdir -p api-lab
cat > api-lab/old.yaml <<'EOF'
apiVersion: extensions/v1beta1
kind: Deployment
metadata:
  name: api-demo
spec:
  replicas: 2
  template:
    metadata:
      labels:
        app: api-demo
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
EOF
kubectl api-versions | grep -E '^(apps/v1|extensions/v1beta1)$'
rg -n 'apiVersion: (extensions/v1beta1|apps/v1beta1|networking.k8s.io/v1beta1|batch/v1beta1)' api-lab
```

Đọc [Deprecation Guide](https://kubernetes.io/docs/reference/using-api/deprecation-guide/) tương ứng phiên bản cluster. `apps/v1` Deployment yêu cầu selector khớp Pod labels. Viết manifest mới:

```bash
cat > api-lab/new.yaml <<'EOF'
apiVersion: apps/v1
kind: Deployment
metadata:
  name: api-demo
spec:
  replicas: 2
  selector:
    matchLabels:
      app: api-demo
  template:
    metadata:
      labels:
        app: api-demo
    spec:
      containers:
      - name: nginx
        image: nginx:1.27
EOF
kubectl create namespace api-lab
kubectl -n api-lab apply --dry-run=server -f api-lab/new.yaml
kubectl -n api-lab apply -f api-lab/new.yaml
kubectl -n api-lab rollout status deployment/api-demo
kubectl -n api-lab get deployment api-demo -o jsonpath='{.apiVersion}{"\n"}'
```

Kết quả: discovery có `apps/v1`, server dry-run chấp nhận file mới, Deployment rollout thành công. Nếu muốn thấy lỗi cũ, thử `kubectl -n api-lab apply --dry-run=server -f api-lab/old.yaml`; cluster có thể báo `no matches for kind` hoặc lỗi schema. Nếu cluster vẫn phục vụ version cũ, lệnh có thể chỉ cảnh báo: kết quả phụ thuộc phiên bản.

**Quy trình thực tế:** lấy `kubectl version`, tra guide cho bản đang chạy và bản sắp nâng cấp, quét cả manifest sinh ra từ `kubectl kustomize`/`helm template`, sửa schema, server dry-run trên cluster đích, kiểm thử rollout rồi tìm client còn gọi version cũ. Không dùng `kubectl convert` nếu chưa cài plugin đó; công cụ này không tích hợp sẵn trong `kubectl` hiện nay.

Trên thực tế migration API cần kiểm tra schema, không chỉ sửa tên version.

Ví dụ:

| API cũ |	API mới|
|--------------|---------------|
| backend.serviceName |	backend.service.name |
| backend.servicePort |	backend.service.port.number|
| Không bắt buộc pathType |	Bắt buộc pathType|

## Dọn lab

```bash
kubectl delete namespace api-lab
rm -r api-lab
```
