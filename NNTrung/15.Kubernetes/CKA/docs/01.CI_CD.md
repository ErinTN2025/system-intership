# CI-CD 
## 1. Khái niệm Continuous Integration- Tích hợp liên tục
- Ý tưởng cốt lõi: mỗi khi dev commit/push code, hệ thống tự động build+test ngay lập tức thay vì đợi đến cuối sprint mới gộp code.
- Mục đích: phát hiện lỗi sớm, tránh "merge hell" khi nhiều người cùng sửa code.
- Các bước điển hình: checkout code -> cài dependencies -> build -> chạy unit test/lint -> tạo artifact (ví dụ: Docker image).
 

## 2. Hiểu tại sao CI ra đời
Hãy tưởng tượng một team 5 dev cùng làm 1 dự án, không có CI:
- Mỗi người code trên máy riêng cả tuần, không đụng vào code của nhau.
- Đến thứ 6, cả 5 người cùng merge code vào nhánh chính `(main)`.
- Kết quả: xung đột code (conflict) khắp nơi, code người này phá code người kia, build lỗi tùm lum, không biết ai gây ra lỗi gì — gọi là "Integration Hell".

- CI ra đời để giải quyết đúng vấn đề này: thay vì gộp code 1 lần/tuần, hãy gộp code liên tục, nhiều lần/ngày, và mỗi lần gộp đều tự động kiểm tra ngay (build + test). Nếu lỗi, phát hiện trong vài phút, không phải vài tuần sau.
- Định nghĩa chuẩn: CI là thực hành mà các developer thường xuyên (nhiều lần/ngày) merge code vào một nhánh dùng chung, và mỗi lần merge được tự động build và test để phát hiện lỗi sớm nhất có thể.

## 3. CI Architecture
### 3.1 Source Control (Git)
Mọi CI đều bắt đầu từ 1 sự kiện trên Git:
- `push` code lên 1 branch
- Mở `pull request /merge request`
- Tạo `tag` (thường dùng để release)
- Chạy theo lịch (`schedule`/cron)
- Đây gọi là Trigger — sự kiện khởi động pipeline.

### 3.2 CI Server/ CI Runner - nơi thực thi
Khi trigger xảy ra, một CI server (Jenkins, GitHub Actions, GitLab CI, CircleCI...) sẽ:
- Nhận sự kiện (qua webhook)
- Cấp phát 1 môi trường sạch để chạy (thường là container hoặc VM tạm - gọi là Runner hoặc Agent)
- Checkout code về runner đó
- Thực thi các bước đã định nghĩa sẵn
- Mỗi lần chạy là một môi trường hoàn toàn mới, sạch (ephemeral) — không có gì sót lại từ lần chạy trước. Điều này đảm bảo kết quả build đáng tin cậy, không bị ảnh hưởng bởi "rác" từ lần trước.

### 3.3 Pipeline
- Đây là bộ khung định nghĩa công việc.
- Pipeline là 1 file cấu hình (thường là YAML) mô tả: "khi có trigger, hãy làm những bước gì, theo thứ tự nào".
- Cấu trúc phân cấp:
```
Pipeline
 └─ Stage (giai đoạn lớn, VD: Build, Test, Package)
     └─ Job (công việc trong 1 stage, có thể chạy song song)
         └─ Step (lệnh cụ thể trong 1 job, chạy tuần tự)
```
- Ví dụ cụ thể (Github Actions):
```yaml
name: CI Pipeline
on: [push]

jobs:
  build-and-test:       # Job
    runs-on: ubuntu-latest      # Runner
    steps:                      # Các step chạy tuần tự
      - uses: actions/checkout@v4   # Bước 1: Lấy code
      - name: Install dependencies
        run: npm install            # Bước 2: Cài thư viện
      - name: Lint
        run: npm run lint           # Bước 3: Kiểm tra style code
      - name: Run unit tests
        run: npm test               # Bước 4: chạy test
      - name: Build
        run: npm run build          # Bước 5: build ra sản phẩm
```
- Các bước chuẩn trong một CI Pipeline

| # | Bước | Mục đích | Ví dụ công cụ |
| --- | --- | --- | --- |
| 1 | **Checkout** | Lấy code mới nhất về runner | `git clone` |
| 2 | **Install dependencies** | Cài thư viện, package cần thiết | `npm`, `pip`, `maven`, `go mod` |
| 3 | **Lint / Static analysis** | Kiểm tra style, code smell, lỗi tiềm ẩn mà chưa cần chạy code | ESLint, Pylint, SonarQube |
| 4 | **Unit test** | Test từng hàm/module riêng lẻ, chạy nhanh | Jest, JUnit, PyTest |
| 5 | **Build** | Biên dịch / đóng gói code thành sản phẩm chạy được | `mvn package`, `docker build` |
| 6 | **Integration test** | Test các thành phần hoạt động cùng nhau (DB, API...) | Testcontainers |
| 7 | **Security scan** | Quét lỗ hổng bảo mật, dependency có CVE | Trivy, Snyk |
| 8 | **Tạo Artifact** | Đóng gói sản phẩm cuối (jar, docker image, zip...) | Docker, Maven |
| 9 | **Push Artifact lên Registry** | Lưu artifact để bước CD sau này lấy dùng | Docker Hub, Harbor, Nexus, ECR |

### 3.4 Artifact
Là sản phẩm đầu ra của quá trình build - có thể là:
- File thực thi (`.jar`,`.exe`,`.war`)
- Docker image
- Static files (html, Css, Js đã build cho frontend)
- Artifact cần được đặt tên có version rõ ràng (VD: `myapp:1.2.3` hoặc `myapp:${GIT_SHA}`) để sau này biết chính xác artifact nào tương ứng với commit nào — đây là điểm nối quan trọng giữa CI và CD.

### 3.5 Parallel jobs (chạy song song)

Nếu có nhiều loại test độc lập (VD: test frontend và test backend), có thể cho chạy song song thay vì tuần tự để tiết kiệm thời gian tổng.

### 3.6 Matrix build

Chạy cùng 1 job nhưng với nhiều tổ hợp môi trường khác nhau cùng lúc — ví dụ test trên cả Node 18, 20, 22 hoặc cả Linux/Windows/Mac.

### 3.7 Secrets Management

Pipeline thường cần thông tin nhạy cảm (API key, mật khẩu DB...) — không bao giờ hard-code vào file YAML, mà lưu trong "Secrets" của CI server (GitHub Secrets, Jenkins Credentials...) rồi gọi ra qua biến môi trường.

### 3.8 Status Check / Branch Protection

Kết hợp CI với Git: có thể cấu hình không cho merge Pull Request nếu CI pipeline chưa pass — đây là cách CI thực sự "bảo vệ" chất lượng code, biến CI từ "công cụ thông báo" thành "cổng chặn" (gate).

### 3.9 Badge / Notification

CI thường tích hợp gửi thông báo (Slack, email) khi pipeline fail, và hiển thị "badge" (passing/failing) trên README của repo.

### 3.10 Caching
Để pipeline chạy nhanh, CI server thường cache lại những thứ ít thay đổi (VD: thư mục node_modules, .m2 của Maven) để lần sau không phải tải lại từ đầu. Đây là kỹ thuật tối ưu tốc độ rất hay dùng trong thực tế.

## 4. Các công cụ CI phổ biến
- Jenkins: Mã nguồn mở, tự host, cực kỳ linh hoạt (plugin), nhưng cấu hình/maintain phức tạp
  - Dùng cho: Doanh nghiệp lớn, cần tùy biến sâu, hạ tầng on-premise
- GitHub Actions: Tích hợp sẵn trong GitHub, dễ dùng, có marketplace action.
  - Dự án host trên GitHub, team nhỏ-vừa
- GitLab CI: Tích hợp sẵn trong GitLab, cấu hình bằng `.gitlab-ci.yml`
  - Dự án host trên GitLab
- CircleCI: Cloud-native, nhanh, dễ setup
  - Startup, muốn nhanh gọn không tự host.
- Về bản chất, tất cả đều giống nhau ở tư duy (trigger → job → step), chỉ khác cú pháp YAML và hệ sinh thái plugin/action.


## 5. CD

### 5.1 Lý do cần CD
CI giải quyết xong bài toán "code có chạy được không, có bug không" — nhưng còn một vấn đề khác:

Tưởng tượng team đã có artifact (docker image) sẵn sàng, nhưng việc đưa nó lên production vẫn làm thủ công: một bạn DevOps SSH vào server, pull image mới, chạy vài lệnh, restart service, cầu nguyện không lỗi. Vấn đề:
- Dễ sai sót do thao tác tay (quên bước, gõ nhầm lệnh).
- Không nhất quán giữa các lần deploy (lần này làm khác lần trước).
- Không có lịch sử rõ ràng: ai deploy, lúc nào, version nào.
- Muốn rollback thì cũng phải làm tay lại từ đầu.

CD ra đời để tự động hóa toàn bộ quá trình từ "có artifact" đến "chạy trên môi trường đích", theo cách nhất quán, có thể lặp lại, và có thể rollback dễ dàng.

### 5.2 Khái niệm
- CD có 2 nghĩa
-  Continuous Delivery: Code luôn ở trạng thái sẵn sàng deploy, nhưng việc deploy lên production cần người bấm nút (manual approval).
  - Mức độ rủi ro: thấp hơn (có bước kiểm soát)
  - Dùng ngành tài chính, y tế, hệ thống cần tuân thủ (compliance)
- Continous Deployment: Tự động deploy thẳng lên production, không cần người can thiệp
  - Mức độ rủi ro Cao hơn( phải rất tự tin vào test)
  - Sản phẩm SaaS, web app, team tự tin vào test coverage cao.

- Cả hai đều "Continuous" (liên tục sẵn sàng), khác nhau ở dấu chấm cuối cùng trước khi chạm production — Delivery dừng lại chờ người, Deployment thì đi thẳng luôn.

## 6. Luồng hoạt động của CD
- Mô hình PUSH (truyền thống — Jenkins, GitLab CI kiểu cũ)
```
Pipeline (Jenkins/GitLab) 
   → chạy lệnh kubectl apply / helm upgrade 
   → ĐẨY thẳng thay đổi vào cluster
```
  - Pipeline CI/CD cần có quyền truy cập trực tiếp vào cluster (kubeconfig, credentials).
  - Vấn đề: pipeline trở thành điểm có quyền lực rất lớn (ai kiểm soát pipeline = kiểm soát cluster) → rủi ro bảo mật.
  - Cluster không có "nguồn sự thật" rõ ràng — trạng thái cluster phụ thuộc vào lịch sử các lần chạy pipeline, khó biết chính xác cấu hình hiện tại là gì nếu không lục lại log.
### 6.2 Mô hình Pull(GitOps - Argo CD)
```
Dev cập nhật Git repo (VD: đổi image tag trong manifest)
   → Agent trong cluster (Argo CD) liên tục theo dõi Git
   → Agent tự PHÁT HIỆN thay đổi và TỰ KÉO về áp dụng vào cluster
```
- Cluster không cần cấp quyền ra bên ngoài cho ai cả - an toàn hơn vì Argo CD chạy ngay trong Cluster
- Git repo là nguồn sự thật tuyệt đối, nhìn vào Git là biết chính xác 
- Dễ audit, dễ rollback (chỉ cần `git revert`).

## 7. Các khái niệm trong CD
### 7.1 Environment (Môi trường)
- Một pipeline CD thường đi qua nhiều môi trường theo thứ tự tăng dần độ "thật":
```
Dev → Staging/QA → Production
```
- **Dev**: môi trường thử nghiệm nhanh, không quan trọng nếu lỗi.
- **Staging**: giống production nhất có thể, dùng để test trước khi lên thật.
- **Production**: môi trường người dùng thật đang dùng - mọi thay đổi phải cẩn trọng tối đa.

### 7.2 Promotion
Là hành động đưa cùng một artifact đã pass ở môi trường thấp lên môi trường cao hơn (VD: cùng 1 docker image tag v1.2.3 được promote từ staging lên production).

KHÔNG build lại artifact riêng cho từng môi trường — build 1 lần, dùng chung artifact đó cho mọi môi trường, chỉ thay đổi config (biến môi trường, secrets). Nếu build lại cho mỗi môi trường, bạn không còn chắc chắn "cái đã test ở staging" giống hệt "cái chạy ở production" nữa.

### 7.3 Deployment Strategy (Chiến lược triển khai)
4.3. Deployment Strategy (Chiến lược triển khai)

Đây là phần hay bị hỏi nhất khi phỏng vấn:

Chiến lược	Cách hoạt động	Ưu điểm	Nhược điểm
Recreate	Tắt hết version cũ, bật version mới	Đơn giản	Có downtime
Rolling Update	Thay dần từng instance cũ bằng mới	Không downtime	Có lúc 2 version chạy song song, khó rollback tức thì
Blue-Green	Chạy song song 2 môi trường (Blue=cũ, Green=mới), chuyển traffic tức thì khi sẵn sàng	Rollback tức thì (chuyển traffic ngược lại)	Tốn gấp đôi tài nguyên tạm thời
Canary	Đẩy version mới cho 1 phần nhỏ traffic (VD 5%), theo dõi, rồi tăng dần	Rủi ro thấp nhất, phát hiện lỗi sớm với ít người ảnh hưởng	Phức tạp, cần hệ thống giám sát (metrics) tốt

(Ghi chú: Canary và Blue-Green chính là 2 chiến lược mà Argo Rollouts implement — nên nhớ kỹ phần này vì sẽ gặp lại.)

4.4. Rollback

Khả năng quay lại version trước đó nhanh chóng khi phát hiện version mới có lỗi. Trong GitOps, rollback đơn giản đến mức chỉ cần git revert commit thay đổi, hệ thống tự đồng bộ lại.

4.5. Approval Gate (Cổng phê duyệt)

Trong Continuous Delivery, thường có bước dừng lại chờ người bấm "Approve" trước khi đi tiếp — đặc biệt trước khi lên production. Có thể kèm theo: review checklist, chữ ký phê duyệt (compliance).

4.6. Feature Flag (khái niệm liên quan, hay đi kèm CD nâng cao)

Kỹ thuật cho phép deploy code lên production nhưng chưa bật tính năng cho người dùng thấy — tách biệt hoàn toàn "deploy" và "release". Giúp giảm rủi ro vì code đã ở production nhưng có thể bật/tắt tính năng bằng config mà không cần deploy lại.

4.7. Health Check / Readiness Probe

Sau khi deploy, hệ thống cần biết version mới có thực sự chạy khỏe không trước khi coi là deploy thành công (VD: gọi endpoint /health, kiểm tra CPU/memory, tỷ lệ lỗi request). Đây là nền tảng để Argo Rollouts tự động quyết định "có nên tiếp tục tăng traffic hay rollback".

PHẦN 5: NỐI CI VÀ CD LẠI THÀNH 1 BỨC TRANH HOÀN CHỈNH
1. Dev push code lên Git
2. CI chạy: build + test → tạo Docker image → push image lên Registry (VD: myapp:a1b2c3)
3. Cập nhật manifest (Deployment YAML / Helm values) trỏ tới image mới → commit vào 
   một Git repo riêng cho config (thường gọi là "GitOps repo" hoặc "config repo")
4. CD (theo mô hình Pull - Argo CD) phát hiện Git repo config đã thay đổi
5. Argo CD tự động sync: áp dụng manifest mới vào cluster
6. Argo Rollouts (nếu có) kiểm soát cách chuyển traffic (canary/blue-green), 
   theo dõi metrics, tự rollback nếu lỗi
7. Xong — version mới chạy ổn định trên production

Lưu ý quan trọng: bước 2 (CI) và bước 3-6 (CD) thường tách biệt thành 2 repo khác nhau trong GitOps:

App repo: chứa source code.
Config/Manifest repo: chứa YAML/Helm values mô tả "muốn chạy version nào, config gì".

Việc tách 2 repo này là một pattern rất phổ biến trong GitOps, giúp:

Đổi config (VD: tăng số replicas) không cần build lại code.
Kiểm soát quyền truy cập riêng biệt (dev sửa app repo, ops sửa config repo).
