# Overview
## 1. Nguyên tắc chung
- **Clone source code** từ Git repo chính thức (GitHub/GitLab/Gerrit...)
- **Build từ source** thay vì tải binary/package
- **Sửa code**, test lại
- **Đóng gói lại** thành package riêng (deb/rpm/image/binary) hoặc chạy trực tiếp từ source
- **Deploy bản custom** đó thay cho bản chính thức, thường qua **private repo/registry** nội bộ

### Docker
Docker Engine hiện là dự án mã nguồn mở tên Moby, viết bằng Go.
- Source: `github.com/moby/moby`
- Build: cần Go toolchain, thường build bằng chính container (`make binary` hoặc dùng `hack/make.sh`)
- Sau khi sửa code Go, build ra binary `dockerd`, `docker` (CLI đôi khi là repo riêng `docker/cli`)
- Đóng gói lại thành `.deb`/`.rpm` bằng công cụ có sẵn trong repo (`hack/make/`, hoặc dùng `nfpm`,`fpm`)
- Host package đó lên repo apt/yum nội bộ (ví dụ Aptly, Pulp, hoặc Nexus/Artifactory) rồi trỏ máy client vào đó thay vì `dowload.docker.com`

### 1.2 Kubernetes (K8s)
K8s cũng viết bằng Go, source tại `github.com/kubernetes/kubernetes`, cực lớn (nhiều component: kube-apiserver, kube-scheduler, kubelet, kube-controller-manager...).
- Build bằng `make`(dùng script `build/` có sẵn, build trong container để đảm bảo môi trường đồng nhất)
- Sau khi sửa, build ra các binary hoặc build container image riêng cho từng component (K8s control plane chạy dạng container image, không phải chỉ package hệ điều hành)
- Push image build lại lên private container registry (Harbor, ECR, GCR nội bộ...)
- Trong manifest/Helm chart, trỏ image field về registry nội bộ đó thay vì `registry.k8s.io`

Nhiều công ty còn tạo fork riêng trên GitHub, giữ đồng bộ với upstream bằng cách rebase/merge định kỳ, để dễ quản lý patch.

### 1.3 OpenStack
- Source từng service nằm ở opendev.org/openstack/<tên-service> (OpenStack dùng Gerrit + OpenDev, không chỉ GitHub)
- Vì là Python, "build" chủ yếu là đóng gói (`pip`/`setuptools`, tạo wheel) chứ không compile
- Sửa code Python trực tiếp, sau đó:
  - Đóng gói thành package riêng (deb qua debuild, hoặc rpm qua rpmbuild/tox) rồi đưa vào repo nội bộ
  - Hoặc dùng công cụ triển khai như Kolla-Ansible/Kolla, build container image cho từng service OpenStack, sửa code rồi build lại image, đẩy lên registry nội bộ
  - Hoặc đơn giản deploy trực tiếp bằng virtualenv/pip từ git clone (ít phổ biến ở production nhưng dùng nhiều lúc dev/test)

### 1.4 Điểm chung hạ tầng
- **Internal package/artifact repository**: Nexus, Artifactory, Pulp, Aptly (cho deb/rpm), Harbor (cho container image)
- **CI/CD pipeline**: tự build lại từ source mỗi khi có patch (Jenkins, GitLab CI, GitHub Actions self-hosted)
- **Fork + patch management**: giữ nhánh riêng, theo dõi upstream, có quy trình rebase để không bị lệch quá xa bản gốc (tránh "patch địa ngục" khi upstream update)
- **Versioning riêng**: để phân biệt bản gốc và bản đã patch (ví dụ `1.28.3-company.2`)

### 1.5 3 kiểu lưu trữ

| Loại | Dùng cho | Ví dụ công cụ | Client download |
|------|----------|---------------|-----------------|
| Package repo | deb/rpm(Openstack, binary Linux) | Apply, Pulp, Nexus | `apt/dnf`|
| Container registry | image (Docker, K8s) | Harbor, Artifactory | `docker pull`, `kubectl` qua manifest |
| Git nội bộ | source code, không phải để cài | Gitlab, Gitea | `git clone` (dành cho dev, không phải server production)|

### 1.6 Cơ chế Git: Branch và Tag
Một repo Git không chỉ có 1 dòng code — nó là một cây lịch sử với nhiều nhánh rẽ ra tại các thời điểm khác nhau.
```
main/master  ●───●───●───●───●───●──→ (code mới nhất, đang phát triển)
              \       \
               \       ●───●  stable/2025.2 (nhánh đóng băng tại 1 thời điểm)
                \
                 ●───●───●  stable/2025.1 (nhánh cũ hơn, chỉ nhận bugfix/security patch)
```
- Cách check trên CLI:
```bash
# Clone về, mặc định checkout nhánh main
git clone https://opendev.org/openstack/nova.git
cd nova

# Xem tất cả các nhánh có trên remote
git branch -r
# origin/stable/2025.1
# origin/stable/2025.2
# origin/stable/2026.1
# origin/unmaintained/2024.1
# ...

# Muốn build bản 2025.2 → chuyển sang nhánh đó
git checkout stable/2025.2

# Hoặc muốn đúng 1 bản vá cụ thể → checkout theo tag
git checkout tags/32.0.0    # tương ứng OpenStack 2025.2 (Nova 32.0.0)
```
- Khi CI/CD của công ty build, họ sẽ chỉ định rõ checkout nhánh/tag nào, ví dụ trong pipeline:
```bash
# ví dụ đơn giản hoá 1 job CI
- git clone https://opendev.org/openstack/nova.git
- git checkout stable/2025.2      # chốt đúng phiên bản cần patch
- git apply company-patches/*.patch   # áp patch riêng của công ty
- build & test
- push package/image gắn tag: nova-2025.2-company.1
```
Nghĩa là công ty không tự tạo phiên bản 2025.1/2025.2 — những nhánh đó do cộng đồng OpenStack quản lý sẵn trên OpenDev. Việc của công ty là chọn đúng nhánh/tag làm điểm xuất phát, rồi áp patch riêng lên trên, và tự đặt version string riêng cho bản build của mình để phân biệt với bản gốc (ví dụ hậu tố `-company.1` như trên).

Cùng logic này áp dụng cho Docker (Moby) và Kubernetes — cả hai đều có nhánh `release-x.y` (K8s) hoặc tag theo semver, bạn có muốn mình show ví dụ cụ thể branching của Kubernetes không (nó hơi khác vì K8s dùng semver `vX.Y.Z` thay vì tên cycle)?

## 2. OpenStack SDK và Source Code
| | OpenStack SDK | Git+ sửa source |
|--|-------------|-----------------|
| Người dùng | Dùng OpenStack (đã có sẵn, chạy rồi) | Đội ngũ vận hành/ phát triển hạ tầng |
| Vai trò | Ứng dụng Client / bên ngoài | Đội ngũ vận hành/ phát triển hạ tầng |
| Ví dụ việc làm | Viết script tạo VM, quản lý network, tự động hoá | Thêm tính năng mới cho Nova, sửa bug trong Neutron |
| Chạy ở đâu | Trong ứng dụng của bạn, gọi API ra ngoài | Là chính service OpenStack đang chạy trên control plane|

- Nói đơn giản: SDK là để nói chuyện VỚI OpenStack, git clone là để sửa CHÍNH OpenStack.

### 2.1 Khi nào dùng OpenStack SDK
SDK (`openstacksdk`, viết bằng Python — package `pip install openstacksdk`) dùng khi bạn là người dùng cuối của cụm OpenStack đã chạy sẵn, muốn:
- Viết script tự động tạo/xoá VM, volume, network
- Tích hợp OpenStack vào hệ thống nội bộ (ví dụ: portal tự cấp phát server cho dev)
- Build công cụ quản trị, dashboard riêng
- Terraform provider cho OpenStack cũng dùng cơ chế tương tự (gọi REST API)

```python
import openstack

conn = openstack.connect(cloud='mycloud')
server = conn.compute.create_server(
    name='my-vm', image_id=..., flavor_id=..., networks=[...]
)
```
Ở đây bạn không đụng vào source code Nova/Neutron/Cinder gì cả. Cụm OpenStack có thể do team hạ tầng dựng sẵn (dù là bản gốc hay bản đã customize), bạn chỉ gọi API vào nó thôi. Đây là công việc của application developer / DevOps tự động hoá.

### 2.2 Khi nào git clone + sửa code
Chỉ khi bạn cần thay đổi hành vi/tính năng của chính service OpenStack:
- Nova hiện không hỗ trợ 1 loại scheduler filter mà công ty cần → phải sửa code Nova
- Cần thêm 1 API endpoint riêng không có trong OpenStack gốc
- Fix 1 bug ảnh hưởng công ty nhưng upstream chưa release patch

## 3. Cấu trúc thư mục Nova
### Các Thư mục (Directories / Modules)

* **accelerator** Quản lý các thiết bị tăng tốc phần cứng (Hardware Accelerators như GPU, FPGA) thông qua việc tích hợp với dự án OpenStack Cyborg.


* **api** Điểm tiếp nhận chính của các yêu cầu HTTP/REST API từ người dùng hoặc hệ thống khác gửi đến Nova để tạo, xóa, chỉnh sửa máy ảo.


* **cmd** Chứa các file thực thi chính (CLI entrypoints) để khởi chạy từng tiến trình dịch vụ của Nova (như `nova-api`, `nova-compute`, `nova-scheduler`).


* **compute** Trái tim quản lý chu kỳ sống của máy ảo (tạo, xoá, pause, resume, migrate) và tương tác trực tiếp với các hypervisor thông qua lớp driver `virt`.


* **conductor** Tiến trình trung gian giúp các node `compute` truy cập database một cách an toàn mà không cần kết nối trực tiếp, đồng thời phối hợp các tác vụ phức tạp (như rebuild hay live-migration).


* **conf** Khai báo và định nghĩa tập trung tất cả cấu hình (configuration options) của hệ thống Nova (`nova.conf`).


* **console** Cung cấp dịch vụ proxy (WebSocket, VNC, SPICE, RDP, Serial) để người dùng truy cập vào màn hình điều khiển máy ảo.


* **db** Lớp tương tác với Cơ sở dữ liệu (Database Abstraction Layer) sử dụng SQLAlchemy, xử lý việc lưu trữ và truy vấn dữ liệu của Nova.


* **hacking** Chứa các quy tắc, kiểm tra tuân thủ chuẩn viết code (style checks / flake8 rules) riêng biệt dành cho cộng đồng phát triển Nova.


* **image** Tích hợp và giao tiếp với OpenStack Glance để lấy, tải hoặc lưu trữ các file ảnh đĩa máy ảo (VM Images).


* **keymgr** Giao tiếp với các dịch vụ quản lý khóa an toàn (như OpenStack Barbican) để mã hóa/giải mã đĩa đĩa hoặc dữ liệu nhạy cảm.


* **limit** Quản lý giới hạn tài nguyên (Unified Limits) để đảm bảo người dùng/dự án không vượt quá hạn ngạch (quota) được cấp.


* **locale** Chứa các file đa ngôn ngữ (Translation files) để hỗ trợ hiển thị thông báo lỗi/log theo nhiều ngôn ngữ.


* **network** Lớp tích hợp mạng, chủ yếu giao tiếp với dịch vụ mạng OpenStack Neutron để cấp phát IP, port, VLAN cho máy ảo.


* **notifications** Phát các sự kiện (Telemetry / Audit Events) ra bus tin nhắn (Message Bus) phục vụ theo dõi, giám sát và tính phí (billing).


* **objects** Định nghĩa lớp NovaObject (Versioned Objects). Giúp đóng gói dữ liệu và chuyển đổi giữa dữ liệu trong DB và định nghĩa JSON/RPC, cho phép hệ thống nâng cấp không gián đoạn (rolling upgrades).


* **pci** Quản lý việc passthrough các thiết bị chuẩn PCI (như card mạng SR-IOV, GPU) trực tiếp từ máy chủ vật lý vào máy ảo.


* **policies** Khai báo quy tắc phân quyền người dùng (RBAC - Role-Based Access Control), quy định ai có quyền gọi API nào.


* **privsep** Phân quyền hệ thống (Privilege Separation). Giúp chạy các lệnh root/quyền cao ở một tiến trình riêng biệt để đảm bảo an toàn bảo mật.


* **scheduler** Bộ lập lịch lựa chọn máy chủ vật lý (Compute Node) phù hợp nhất để đặt máy ảo dựa trên tài nguyên trống (CPU, RAM, đĩa...) và các điều kiện lọc/trọng số.


* **servicegroup** Kiểm tra trạng thái sống/chết (Health-check / Heartbeat) của các tiến trình dịch vụ Nova trong hệ thống.


* **share** Tích hợp với dịch vụ chia sẻ file OpenStack Manila (Shared File Systems) cho máy ảo.


* **storage** Tương tác với các hệ thống lưu trữ khối nâng cao (như Ceph/RBD) hoặc đĩa cục bộ.


* **tests** Bộ mã nguồn kiểm thử (Unit tests và Functional tests) để kiểm tra tính chính xác của toàn bộ mã nguồn Nova.


* **virt** Chứa các driver giao tiếp với các công nghệ ảo hóa thực tế bên dưới (KVM/QEMU thông qua `libvirt`, VMware vCenter, Hyper-V,...).


* **volume** Tích hợp với dịch vụ OpenStack Cinder để quản lý việc gắn/tháo đĩa cứng ảo (Block Storage Volume) vào máy ảo.

* **wsgi** Cấu hình và khởi chạy ứng dụng WSGI cho API (cho phép chạy Nova API dưới các web server như Apache2 hoặc uWSGI).

### Các Tệp tin Độc lập (Standalone Files)

* **`__init__.py`** Khai báo mã nguồn là một Python package; thường áp dụng "monkey patch" (sửa đổi thư viện runtime) từ rất sớm nếu dùng Eventlet.


* **`availability_zones.py`** Logic chia cụm hạ tầng thành các Zone khả dụng (Availability Zones / Aggregate Host) cho người dùng lựa chọn khi tạo VM.


* **`baserpc.py`** Định nghĩa lớp giao diện RPC cơ bản chung cho tất cả các dịch vụ Nova.


* **`block_device.py`** Xử lý và chuyển đổi cấu trúc dữ liệu mô tả đĩa cứng (Block Device Mapping - BDM) của máy ảo.


* **`cache_utils.py`** Các hàm tiện ích hỗ trợ lưu dữ liệu đệm (caching) thông qua Memcached hoặc dogpile.cache nhằm tăng tốc độ truy xuất.


* **`config.py`** Tệp đăng ký và nạp các tùy chọn cấu hình toàn cục khi các ứng dụng/dịch vụ bắt đầu khởi chạy.


* **`context.py`** Định nghĩa lớp `RequestContext` lưu trữ ngữ cảnh của mỗi request (User ID, Tenant/Project ID, Auth Token, quyền hạn,...).


* **`crypto.py`** Xử lý các tác vụ mã hóa, tạo chứng chỉ SSL/TLS, cặp khóa SSH cho máy ảo.


* **`exception_wrapper.py`** Decorator hỗ trợ bắt các ngoại lệ (exception) và tự động gửi thông báo lỗi (notification) ra Message Bus.


* **`exception.py`** Định nghĩa tập hợp tất cả các lớp ngoại lệ (lỗi tùy chỉnh) của riêng Nova (ví dụ: `InstanceNotFound`, `NoValidHost`).


* **`filesystem.py`** Hỗ trợ các thao tác an toàn trên hệ thống tệp tin vật lý (đọc, ghi, kiểm tra mount point, thao tác sysfs).


* **`filters.py`** Cung cấp cơ chế lọc danh sách chung (dùng cho Scheduler hoặc Loadable Manager).


* **`i18n.py`** Đăng ký hàm dịch thuật chuỗi (gettext `_()`) để phục vụ đa ngôn ngữ.


* **`loadables.py`** Cơ chế dynamically load (tải động) các module/plugin vào hệ thống tại thời điểm runtime.


* **`manager.py`** Định nghĩa lớp cơ sở `Manager` cho các dịch vụ chính (ComputeManager, ConductorManager, SchedulerManager).


* **`middleware.py`** Chứa các lớp Middleware lọc request HTTP (như xử lý CORS, bắt lỗi, kiểm tra header API version).


* **`monkey_patch.py`** Thực hiện kỹ thuật monkey-patching (thay thế thư viện chuẩn của Python bằng phiên bản async/non-blocking).


* **`policy.py`** Tải và thực thi cơ chế kiểm tra quyền thực thi (Enforcer) dựa trên tập policy của dự án.


* **`profiler.py`** Tích hợp với OSProfiler để vết (trace) luồng xử lý của yêu cầu xuyên suốt các dịch vụ trong OpenStack.


* **`quota.py`** Logic kiểm tra và quản lý hạn ngạch tài nguyên (số máy ảo, vCPU, RAM tối đa) của từng Project/User.


* **`rpc.py`** Lớp trừu tượng hóa cho giao tiếp RPC (Remote Procedure Call) giữa các tiến trình Nova qua RabbitMQ / oslo.messaging.


* **`safe_utils.py`** Chứa các hàm tiện ích an toàn (như kiểm tra tham số của hàm, làm sạch dữ liệu) tránh gây exception ngoài ý muốn.


* **`service_auth.py`** Quản lý việc xác thực giữa dịch vụ Nova với các dịch vụ OpenStack khác (Service-to-Service authentication qua Keystone).


* **`service.py`** Khung quản lý vòng đời (khởi tạo, chạy, dừng) của các daemon service trong Nova.


* **`test.py`** Lớp Test Case nền tảng (`TestCase`) chứa cấu hình mock, DB giả lập... mà tất cả các bài unit test của Nova kế thừa.


* **`thread_pool_factory.py`** Quản lý tập trung các luồng thực thi (Thread Pool Executors) giúp tối ưu hóa việc chạy đồng thời và dọn dẹp luồng khi dừng hệ thống.


* **`utils.py`** Tập hợp hàng loạt hàm trợ giúp (helper functions) dùng chung cho toàn bộ mã nguồn (thao tác chuỗi, chạy lệnh shell, mã hóa...).


* **`version.py`** Quản lý thông tin phiên bản phát hành hiện tại của Nova.


* **`vtpm.py`** Hỗ trợ tính năng Virtual TPM (Trusted Platform Module) cho máy ảo để bảo mật khóa/mã hóa.


* **`weights.py`** Cung cấp lớp nền tảng tính toán trọng số (Weigher) dùng trong `nova-scheduler` để xếp hạng các máy chủ vật lý.
