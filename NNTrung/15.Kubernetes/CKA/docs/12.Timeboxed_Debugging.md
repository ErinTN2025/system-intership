# Debug Kubernetes theo thời gian giới hạn

## Lý thuyết cốt lõi

Khi chỉ có vài phút, đi từ dấu hiệu rộng tới nguyên nhân cụ thể: **context/namespace → workload → Pod/Events → logs → Service/EndpointSlice → cấu hình**. Trước mỗi lệnh, hỏi nó sẽ loại trừ giả thuyết nào. `kubectl get` cho trạng thái, `describe` cho điều kiện và Events, `logs --previous` cho container vừa crash, `rollout status` cho Deployment, EndpointSlice cho backend thật của Service. `kubectl debug` thêm ephemeral container khi image ứng dụng thiếu shell/công cụ; quyền RBAC và Pod Security có thể chặn thao tác này.

Phân biệt lỗi thường gặp:

| Dấu hiệu | Kiểm tra đầu tiên |
| --- | --- |
| `Pending` | `describe pod`: taint, tài nguyên, PVC, affinity |
| `ImagePullBackOff` | image/tag, registry, imagePullSecret, Events |
| `CrashLoopBackOff` | `logs --previous`, command/args, config, probe |
| Pod Running nhưng không Ready | readiness probe và log ứng dụng |
| Service không có backend | selector, Pod labels, readiness, EndpointSlice |
| Service có backend nhưng request lỗi | port/targetPort, app listener, NetworkPolicy, DNS |

## Bài tập 8 phút: Service trỏ sai Pod

Yêu cầu: cluster lab, `kubectl`, shell Bash. Đặt đồng hồ **8 phút**. Tạo tình huống:

```bash
kubectl create namespace debug-lab
kubectl -n debug-lab create deployment web --image=nginx:1.27 --replicas=2
kubectl -n debug-lab rollout status deployment/web
kubectl -n debug-lab expose deployment web --name=web --port=80 --target-port=80
kubectl -n debug-lab patch service web --type=merge -p '{"spec":{"selector":{"app":"wrong"}}}'
```

**Đề bài:** Pod chạy nhưng Service `web` không có backend. Tìm và sửa nguyên nhân trong 8 phút; không xóa/tạo lại Deployment.

Gợi ý trình tự khi bí:

```bash
kubectl config current-context
kubectl -n debug-lab get deployment,pods,service,endpointslice -o wide
kubectl -n debug-lab describe service web
kubectl -n debug-lab get service web -o jsonpath='{.spec.selector}{"\n"}'
kubectl -n debug-lab get pods --show-labels
kubectl -n debug-lab get endpointslice -l kubernetes.io/service-name=web
```

**Đáp án:** Service selector là `app=wrong`, Pod có `app=web`. Sửa và xác nhận:

```bash
kubectl -n debug-lab patch service web --type=merge -p '{"spec":{"selector":{"app":"web"}}}'
kubectl -n debug-lab get endpointslice -l kubernetes.io/service-name=web
kubectl -n debug-lab run curl --image=curlimages/curl:8.8.0 --restart=Never --rm -i -- curl -fsS --max-time 5 http://web
```

Kết quả: EndpointSlice có địa chỉ Pod Ready và `curl` trả trang nginx. Nếu Pod curl không chạy do policy/image pull, dùng `kubectl -n debug-lab port-forward service/web 8080:80` rồi truy cập `http://localhost:8080` ở terminal khác. `port-forward` kiểm tra đường tới Service nhưng không thay cho bài kiểm tra DNS và network nội bộ Pod.

## Bài tập 5 phút: container crash

```bash
kubectl -n debug-lab create deployment broken --image=busybox:1.36 -- sh -c 'echo missing-config >&2; exit 1'
kubectl -n debug-lab get pods -l app=broken
kubectl -n debug-lab describe pod -l app=broken
kubectl -n debug-lab logs deployment/broken --previous
```

Nếu container chưa restart, `--previous` có thể chưa có log; dùng `kubectl -n debug-lab logs deployment/broken`. Nguyên nhân được ứng dụng in ra là `missing-config`, không phải lỗi scheduling. Trong hệ thống thật, xác minh ConfigMap/Secret được tham chiếu và giá trị env/volume trước khi sửa. Với image không có shell, cân nhắc `kubectl debug -it <pod> --image=busybox:1.36 --target=<container> -- sh`; kết quả phụ thuộc runtime, RBAC và policy.

## Mẫu xử lý nhanh trong kỳ thi/sự cố

1. **0–1 phút:** xác nhận context, namespace, tên resource và triệu chứng.
2. **1–3 phút:** `get`, `describe`, Events; xác định lớp lỗi (API, scheduler, image, app hay network).
3. **3–6 phút:** dùng một lệnh kiểm chứng giả thuyết chính (`logs --previous`, selector/EndpointSlice, PVC, probe).
4. **6–8 phút:** sửa tối thiểu, `rollout status`/`get endpointslice`/request thử, ghi lại nguyên nhân.

Không áp dụng thời gian cố định máy móc: nếu Events đã chỉ rõ lỗi, sửa ngay và dành thời gian xác nhận. Tránh thay nhiều trường cùng lúc vì khó biết thay đổi nào giải quyết vấn đề.

## Tự kiểm tra

1. Pod Running có bảo đảm Service có endpoint không?
2. Khi nào dùng `logs --previous`?
3. Pod Pending thì kiểm tra log ứng dụng hay Events trước?

## Dọn lab

```bash
kubectl delete namespace debug-lab
```
