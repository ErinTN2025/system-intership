# ServiceAccount token, Linux capabilities và Pod Security Standards

## Lý thuyết cốt lõi

**ServiceAccount (SA)** là danh tính của workload khi gọi Kubernetes API. Pod mặc định dùng SA `default` của namespace; quyền API do RBAC quyết định, không do tên SA. Kubernetes hiện dùng token được cấp cho Pod qua projected volume, có thời hạn và ràng buộc với Pod. Chỉ bật mount token khi ứng dụng cần gọi API; đặt `automountServiceAccountToken: false` ở SA hoặc Pod để bỏ mount tự động. Giá trị ở Pod được ưu tiên. Tránh tạo token Secret dài hạn nếu không có lý do rõ ràng.

**Linux capabilities** chia quyền root thành các khả năng nhỏ hơn. `securityContext.capabilities.drop: [ALL]` bỏ tất cả, chỉ thêm lại khả năng thật sự cần, ví dụ `NET_BIND_SERVICE` khi bind cổng thấp. Capabilities không thay RBAC và chỉ áp dụng Linux.

**Pod Security Standards (PSS)** định nghĩa ba mức `privileged`, `baseline`, `restricted`. Pod Security Admission áp chính sách đó bằng label namespace. Restricted yêu cầu nhiều điều kiện cùng lúc: chạy non-root, seccomp, không privilege escalation, drop ALL capabilities, loại volume hợp lệ, v.v. Mức tuân thủ phụ thuộc version chính sách; `enforce-version=latest` thay đổi khi nâng cluster, môi trường production nên pin version đã kiểm thử.

## Lab 1: SA và token

Yêu cầu: cluster lab và quyền tạo namespace, SA, Pod. Dùng Bash.

```bash
kubectl create namespace identity-lab
kubectl -n identity-lab create serviceaccount reader
kubectl -n identity-lab apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: token-on
spec:
  serviceAccountName: reader
  containers:
  - name: app
    image: busybox:1.36
    command: [sh, -c, 'ls /var/run/secrets/kubernetes.io/serviceaccount; sleep 3600']
EOF
kubectl -n identity-lab wait --for=condition=Ready pod/token-on --timeout=120s
kubectl -n identity-lab logs token-on
kubectl -n identity-lab auth can-i list pods --as=system:serviceaccount:identity-lab:reader
```

Kết quả: token/CA/namespace được mount, nhưng SA mới không mặc nhiên có quyền list Pod. Không in nội dung token ra terminal/log.

Tạo Pod không mount token:

```bash
kubectl -n identity-lab apply -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: token-off
spec:
  serviceAccountName: reader
  automountServiceAccountToken: false
  containers:
  - name: app
    image: busybox:1.36
    command: [sh, -c, 'ls /var/run/secrets/kubernetes.io/serviceaccount 2>&1 || true; sleep 3600']
EOF
kubectl -n identity-lab wait --for=condition=Ready pod/token-off --timeout=120s
kubectl -n identity-lab logs token-off
```

Kết quả: đường dẫn token không tồn tại. Chỉ cấp RBAC khi ứng dụng thật sự cần; kiểm tra quyền bằng `auth can-i` trước khi thêm Role/RoleBinding.

## Lab 2: capabilities và restricted

```bash
kubectl label namespace identity-lab pod-security.kubernetes.io/enforce=restricted
kubectl label namespace identity-lab pod-security.kubernetes.io/enforce-version=latest
kubectl -n identity-lab apply --dry-run=server -f - <<'EOF'
apiVersion: v1
kind: Pod
metadata:
  name: secure-web
spec:
  serviceAccountName: reader
  automountServiceAccountToken: false
  securityContext:
    runAsNonRoot: true
    runAsUser: 101
    seccompProfile:
      type: RuntimeDefault
  containers:
  - name: web
    image: nginxinc/nginx-unprivileged:1.27
    ports:
    - containerPort: 8080
    securityContext:
      allowPrivilegeEscalation: false
      capabilities:
        drop: [ALL]
EOF
```

Nếu được chấp nhận, chạy lại với `apply -f -` và xem `kubectl -n identity-lab describe pod secure-web`. Thử bỏ `drop: [ALL]` trong file thử để quan sát lỗi admission. Thử thêm `NET_ADMIN`: restricted sẽ từ chối; `NET_BIND_SERVICE` là capability duy nhất được thêm lại theo PSS restricted cho Linux. Pod cũ không bị xóa khi namespace vừa được gắn nhãn enforce; policy kiểm tra request tạo/cập nhật Pod tiếp theo.

## Tự kiểm tra

1. SA có token nhưng không có RoleBinding thì có quyền list Pod không?
2. Vì sao `automountServiceAccountToken: false` không thay thế RBAC?
3. PSS restricted cho phép thêm lại capability nào?
