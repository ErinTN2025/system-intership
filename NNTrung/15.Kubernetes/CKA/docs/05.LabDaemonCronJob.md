# Phần A — DaemonSet

DaemonSet bảo đảm mỗi node đủ điều kiện chạy một Pod. Nó thường được dùng cho log collector, monitoring agent, CNI, CSI node plugin hoặc security agent. [Tài liệu DaemonSet chính thức](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/).

## Lab A1 — Chạy một Pod trên mỗi node

Tạo DaemonSet:

```bash
kubectl apply -f - <<'EOF'
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: node-agent
spec:
  selector:
    matchLabels:
      app: node-agent
  template:
    metadata:
      labels:
        app: node-agent
    spec:
      tolerations:
        - key: node-role.kubernetes.io/control-plane
          operator: Exists
          effect: NoSchedule
        - key: node-role.kubernetes.io/master
          operator: Exists
          effect: NoSchedule
      containers:
        - name: agent
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              while true; do
                echo "$(date) - pod=$HOSTNAME - node-file=$(cat /host/etc/hostname)"
                sleep 20
              done
          resources:
            requests:
              cpu: 10m
              memory: 16Mi
            limits:
              cpu: 50m
              memory: 32Mi
          volumeMounts:
            - name: host-hostname
              mountPath: /host/etc/hostname
              readOnly: true
      volumes:
        - name: host-hostname
          hostPath:
            path: /etc/hostname
            type: File
EOF
```
- Trong Kubernetes, các node control-plane (master) mặc định được gắn taint để "đuổi" các pod thông thường không cho chạy trên đó, ví dụ:
```
node-role.kubernetes.io/control-plane:NoSchedule
```
Một Pod chỉ được phép scheduler đưa vào node có taint đó nếu pod đó khai báo `toleration` tương ứng - nghĩa là pod "chịu đựng" (tolerate) được taint đó.

- **Chốt lại**: Taint nằm trên Node (chặn pod vào), Toleration nằm trên Pod (cho phép pod bỏ qua taint đó).

- Đây là DaemonSet dùng để chạy **node-agent** — mục đích thường là chạy **trên mọi node trong cluster**, kể cả node control-plane. Nếu không có `tolerations`, pod của DaemonSet sẽ không bao giờ được schedule lên các node master/control-plane, vì các node đó có taint mặc định chặn pod thường.

| Toleration |	Ý nghĩa |
|--------------|-------|
| `node-role.kubernetes.io/control-plane` |	Taint key dùng trên Kubernetes bản mới (≥ 1.20)|
| `node-role.kubernetes.io/master`|	Taint key dùng trên Kubernetes bản cũ hơn|

- Khai báo cả hai để đảm bảo pod chạy được trên control-plane node dù cluster dùng phiên bản nào.
  - `key`: tên của taint mà pod sẽ tolerant
  - `operator: Exists`: nghĩa là chỉ taint có key này tồn tại trên node (không quan tâm giá trị `value`) thì toleration sẽ khớp. ( Ngược lại với `operator: Equal`, phải khớp cả `key` và `value`).
  - `effect: NoSchedule`: chỉ tolerate loại taint có effect là `NoSchedule` - nghĩa là "không cho pod mới được schedule vào, nhưng pod đang chạy sẵn thì không bị đuổi." Các effect khác gồn `PreferNoSchedule`(ưu tiên tránh) và `NoExecute` (đuổi cả pod đang chạy).

Kiểm tra:

```bash
kubectl get daemonset
kubectl get pods -o wide
kubectl describe daemonset node-agent
```

So sánh:

```bash
kubectl get nodes --no-headers | wc -l
kubectl get pods -l app=node-agent --no-headers | wc -l
```

Nếu có hai node, thông thường sẽ có hai Pod.

Xem log từ tất cả Pod:

```bash
kubectl logs -l app=node-agent --prefix --tail=5
```

### Điều cần quan sát

- Mỗi Pod nằm trên một node khác nhau.
- DaemonSet không có trường `replicas`.
- Số Pod mong muốn được tính từ số node đủ điều kiện.
- `hostPath` cho phép Pod đọc file từ node chứa nó.
- Toleration giúp Pod có thể chạy trên control-plane node bị taint.

## Lab A2 — Chỉ chạy trên một nhóm node

Xem tên node:

```bash
kubectl get nodes
```

Gắn label cho một node worker. Thay `<NODE_NAME>` bằng tên node:

```bash
kubectl label node <NODE_NAME> disk=ssd
```

Thêm `nodeSelector` vào DaemonSet:

```bash
kubectl patch daemonset node-agent --type merge -p '
spec:
  template:
    spec:
      nodeSelector:
        disk: ssd
'
```

Quan sát:

```bash
kubectl get pods -l app=node-agent -o wide -w
```

Nhấn `Ctrl+C` sau khi rollout ổn định.

Kiểm tra:

```bash
kubectl get daemonset node-agent
kubectl describe daemonset node-agent
```

Kết quả mong đợi: chỉ node có `disk=ssd` chạy Pod của DaemonSet.

Khôi phục chạy trên mọi node:

```bash
kubectl patch daemonset node-agent --type json \
  -p='[{"op":"remove","path":"/spec/template/spec/nodeSelector"}]'
```

## Lab A3 — Rolling update DaemonSet

Thay đổi annotation của Pod template để kích hoạt rollout:

```bash
kubectl patch daemonset node-agent --type merge -p '
spec:
  template:
    metadata:
      annotations:
        lab-version: v2
'
```

Theo dõi:

```bash
kubectl rollout status daemonset/node-agent
kubectl rollout history daemonset/node-agent
kubectl get pods -l app=node-agent -o wide
```

Thử xóa một Pod:

```bash
POD_NAME=$(kubectl get pod -l app=node-agent \
  -o jsonpath='{.items[0].metadata.name}')

kubectl delete pod "$POD_NAME"
kubectl get pods -l app=node-agent -o wide -w
```

DaemonSet sẽ tạo Pod thay thế trên node tương ứng.

# Phần B — Job

Job dùng cho tác vụ chạy đến khi hoàn thành, chẳng hạn migration database, backup, xử lý batch hoặc tạo báo cáo. Job chỉ chấp nhận `restartPolicy: Never` hoặc `OnFailure`. [Tài liệu Job chính thức](https://kubernetes.io/docs/concepts/workloads/controllers/job/).

## Lab B1 — Job đơn giản

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: calculate
spec:
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: calculate
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              echo "Job started at $(date)"
              result=$((25 * 4))
              echo "Result: $result"
              sleep 5
              echo "Job completed"
EOF
```

Theo dõi:

```bash
kubectl get jobs
kubectl get pods -l job-name=calculate -w
```

Xem log:

```bash
kubectl logs job/calculate
kubectl describe job calculate
```

Kiểm tra condition:

```bash
kubectl get job calculate \
  -o jsonpath='{range .status.conditions[*]}{.type}={.status}{"\n"}{end}'
```

Kết quả mong đợi:

```text
Complete=True
```

## Lab B2 — Retry và backoffLimit

Tạo một Job luôn thất bại:

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: always-fail
spec:
  backoffLimit: 2
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: fail
          image: busybox:1.36
          command:
            - sh
            - -c
            - |
              echo "Attempt from pod $HOSTNAME"
              exit 1
EOF
```

Theo dõi:

```bash
kubectl get pods -l job-name=always-fail -w
```

Sau khi Job ngừng retry:

```bash
kubectl get job always-fail
kubectl get pods -l job-name=always-fail
kubectl describe job always-fail
```

Xem log tất cả Pod:

```bash
for pod in $(kubectl get pod -l job-name=always-fail -o name); do
  echo "===== $pod ====="
  kubectl logs "$pod"
done
```

### Điều cần hiểu

- `backoffLimit: 2` không có nghĩa tổng cộng chỉ có hai Pod.
- Job thất bại khi số lần retry vượt quá giới hạn.
- Các lần retry có khoảng chờ tăng dần.
- `restartPolicy: Never` tạo Pod mới cho mỗi lần thử.
- Với `OnFailure`, kubelet có thể restart container trong cùng Pod.

## Lab B3 — Giới hạn thời gian chạy

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: deadline-demo
spec:
  activeDeadlineSeconds: 15
  backoffLimit: 1
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: worker
          image: busybox:1.36
          command: ["sh", "-c", "echo Starting; sleep 60; echo Finished"]
EOF
```

Quan sát:

```bash
kubectl get job deadline-demo -w
```

Sau khoảng 15 giây:

```bash
kubectl describe job deadline-demo
```

Job phải thất bại với lý do liên quan đến `DeadlineExceeded`.

Phân biệt:

- `activeDeadlineSeconds`: giới hạn tổng thời gian của Job.
- `backoffLimit`: giới hạn retry do Pod thất bại.
- `ttlSecondsAfterFinished`: thời gian giữ Job sau khi đã hoàn thành.

## Lab B4 — Parallel Indexed Job

Tạo sáu tác vụ và chạy tối đa hai tác vụ cùng lúc:

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: Job
metadata:
  name: indexed-workers
spec:
  completions: 6
  parallelism: 2
  completionMode: Indexed
  ttlSecondsAfterFinished: 300
  template:
    spec:
      restartPolicy: Never
      containers:
        - name: worker
          image: busybox:1.36
          env:
            - name: JOB_INDEX
              valueFrom:
                fieldRef:
                  fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index']
          command:
            - sh
            - -c
            - |
              echo "Worker index=$JOB_INDEX pod=$HOSTNAME started"
              sleep $((JOB_INDEX + 3))
              echo "Worker index=$JOB_INDEX completed"
EOF
```

Theo dõi:

```bash
kubectl get pods -l job-name=indexed-workers -w
```

Xem trạng thái Job:

```bash
kubectl get job indexed-workers
kubectl describe job indexed-workers
```

Xem kết quả:

```bash
kubectl logs job/indexed-workers --prefix
```

### Các trường quan trọng

| Trường | Ý nghĩa |
| --- | --- |
| `completions: 6` | Cần sáu lần hoàn thành thành công |
| `parallelism: 2` | Tối đa hai Pod xử lý đồng thời |
| `completionMode: Indexed` | Mỗi lần hoàn thành có index riêng từ 0 đến 5 |
| `ttlSecondsAfterFinished` | Tự dọn Job sau khi kết thúc |

## Thử suspend Job

Tạo lại Job nếu nó đã hoàn thành quá nhanh:

```bash
kubectl patch job indexed-workers --type merge -p '{"spec":{"suspend":true}}'
kubectl get job indexed-workers
```

Lưu ý: suspend một Job đang chạy sẽ xóa các Pod active; khi resume, Job tiếp tục hướng tới số completion yêu cầu.

Resume:

```bash
kubectl patch job indexed-workers --type merge -p '{"spec":{"suspend":false}}'
```

# Phần C — CronJob

CronJob tạo Job theo lịch. Việc schedule không bảo đảm tuyệt đối “đúng một lần”, nên tác vụ cần có tính idempotent. [Tài liệu CronJob chính thức](https://kubernetes.io/docs/concepts/workloads/controllers/cron-jobs/).

## Lab C1 — CronJob chạy mỗi phút

```bash
kubectl apply -f - <<'EOF'
apiVersion: batch/v1
kind: CronJob
metadata:
  name: report-generator
spec:
  schedule: "* * * * *"
  timeZone: "Etc/UTC"
  concurrencyPolicy: Forbid
  startingDeadlineSeconds: 30
  successfulJobsHistoryLimit: 3
  failedJobsHistoryLimit: 1
  jobTemplate:
    spec:
      backoffLimit: 1
      template:
        spec:
          restartPolicy: Never
          containers:
            - name: report
              image: busybox:1.36
              command:
                - sh
                - -c
                - |
                  echo "Generating report"
                  echo "Time: $(date -u)"
                  echo "Pod: $HOSTNAME"
                  sleep 5
                  echo "Report completed"
EOF
```

Theo dõi:

```bash
kubectl get cronjob
kubectl get jobs -w
```

Sau khi có Job:

```bash
kubectl get cronjob report-generator
kubectl get jobs --sort-by=.metadata.creationTimestamp
kubectl get pods --sort-by=.metadata.creationTimestamp
```

Xem log Job mới nhất:

```bash
LATEST_JOB=$(kubectl get jobs \
  --sort-by=.metadata.creationTimestamp \
  -o jsonpath='{.items[-1:].metadata.name}')

kubectl logs "job/$LATEST_JOB"
```

## Hiểu cron expression

```text
┌──────── phút        0–59
│ ┌────── giờ         0–23
│ │ ┌──── ngày/tháng  1–31
│ │ │ ┌── tháng       1–12
│ │ │ │ ┌ ngày/tuần   0–6
│ │ │ │ │
* * * * *
```

Ví dụ:

```text
*/5 * * * *      Mỗi 5 phút
0 * * * *        Đầu mỗi giờ
0 2 * * *        02:00 mỗi ngày
0 2 * * 1        02:00 mỗi thứ Hai
0 0 1 * *        00:00 ngày đầu mỗi tháng
```

Dùng `spec.timeZone`; không đặt `TZ=` hoặc `CRON_TZ=` bên trong `schedule`.

## Lab C2 — concurrencyPolicy

Ba giá trị:

| Chính sách | Hành vi |
| --- | --- |
| `Allow` | Cho phép nhiều Job chạy đồng thời |
| `Forbid` | Bỏ qua lần mới nếu Job trước chưa xong |
| `Replace` | Dừng Job cũ và thay bằng Job mới |

Cho Job chạy 90 giây trong khi lịch chạy mỗi phút:

```bash
kubectl patch cronjob report-generator --type merge -p '
spec:
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: report
              image: busybox:1.36
              command:
                - sh
                - -c
                - echo "Started $(date -u)"; sleep 90; echo "Completed $(date -u)"
'
```

Theo dõi trong khoảng hai phút:

```bash
kubectl get cronjob,jobs,pods -w
```

Vì dùng `Forbid`, lần schedule tiếp theo sẽ không tạo Job song song nếu Job cũ vẫn chạy.

Xem event:

```bash
kubectl describe cronjob report-generator
```

## Lab C3 — Suspend và chạy thủ công

Tạm dừng schedule:

```bash
kubectl patch cronjob report-generator \
  --type merge \
  -p '{"spec":{"suspend":true}}'

kubectl get cronjob report-generator
```

`suspend` chỉ ngăn tạo Job mới; nó không dừng Job đã tồn tại.

Chạy thủ công từ CronJob:

```bash
kubectl create job \
  --from=cronjob/report-generator \
  report-manual
```

Kiểm tra:

```bash
kubectl get job report-manual
kubectl logs job/report-manual
```

Bật lại:

```bash
kubectl patch cronjob report-generator \
  --type merge \
  -p '{"spec":{"suspend":false}}'
```

- Mỗi Pod sleep từ 3–10 giây.

- Có thể suspend và chạy thủ công.

# Phần E — Debug challenge

## Lỗi 1: DaemonSet không tạo Pod

```yaml
selector:
  matchLabels:
    app: agent
template:
  metadata:
    labels:
      app: different-agent
```

Tìm lỗi bằng:

```bash
kubectl apply -f broken.yaml
kubectl describe daemonset <name>
```

Nguyên nhân: selector không khớp Pod template label.

## Lỗi 2: Job không được chấp nhận

```yaml
restartPolicy: Always
```

Job chỉ cho phép:

```yaml
restartPolicy: Never
```

hoặc:

```yaml
restartPolicy: OnFailure
```

## Lỗi 3: CronJob không tạo Job

Kiểm tra:

```bash
kubectl get cronjob
kubectl describe cronjob <name>
kubectl get events --sort-by=.lastTimestamp
```

Các nguyên nhân thường gặp:

- `suspend: true`.
- Cron expression sai.
- `startingDeadlineSeconds` quá ngắn.
- Job trước còn chạy và `concurrencyPolicy: Forbid`.
- CronJob/controller vừa bị gián đoạn hoặc clock sai.
