# CKS: audit, runtime detection và incident lab (roadmap tuần 18)

## Lý thuyết cốt lõi

Kubernetes audit ghi **ai gọi API nào**, qua các stage như `RequestReceived`, `ResponseComplete`; log ứng dụng ghi hành vi của app; runtime detector quan sát process/file/network trên node. Chúng bổ sung nhau. Incident flow: detect → contain → preserve evidence → investigate → eradicate → recover. Xóa Pod quá sớm có thể mất log và dấu vết; cô lập theo phạm vi nhỏ nhất.

## Lab A: audit API

**Môi trường:** VM kubeadm snapshot. Tạo audit policy lab ghi metadata của `pods`, `secrets` và request `create/delete`; cấu hình `--audit-policy-file` và `--audit-log-path` của API server theo [tài liệu audit](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/), mount file/đường log vào static Pod. Xác nhận API server khỏe, tạo/xóa ConfigMap thử và tìm audit event theo user, verb, namespace, resource, response code. Chọn policy hẹp để tránh log lớn và tránh ghi nội dung Secret. Ghi lý do `Metadata` level phù hợp hơn `RequestResponse` cho bài này.

## Lab B: sự cố mô phỏng

Cài Falco trên cluster lab theo tài liệu phiên bản tương ứng; xác nhận driver/plugin và event pipeline hoạt động trước khi mô phỏng. Trong Pod thử do bạn tạo, chạy shell/công cụ mạng với một command rõ ràng; tìm alert Falco, thời điểm và Pod/container liên quan. Dùng audit log xác định ai tạo Pod hoặc `exec`. Ghi lại Pod YAML, Events, log ứng dụng, SA/RBAC và image digest; **không copy token/Secret**. Cô lập Pod bằng NetworkPolicy trong namespace lab hoặc scale Deployment về 0 sau khi thu thập bằng chứng; sửa manifest/RBAC; deploy lại và xác nhận workload hợp lệ vẫn chạy, hành vi đáng ngờ bị chặn hoặc được cảnh báo.

**Đạt khi:** postmortem ngắn có timeline, bằng chứng, nguyên nhân, phạm vi ảnh hưởng, cách khôi phục và kiểm tra tái phát. Nếu Falco không chạy do kernel/driver không tương thích, ghi rõ điều kiện thiếu; audit lab vẫn có thể hoàn thành. Xem [nguồn audit/runtime](29.Tai_lieu_tham_khao.md#cks-và-kcsa-security).
