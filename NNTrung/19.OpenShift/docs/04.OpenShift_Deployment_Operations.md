# Vận hành và triển khai ứng dụng trên OpenShift

## 1. Mô hình vận hành

Vòng đời một ứng dụng trên OpenShift nên đi theo chu trình khai báo:

```text
Thiết kế → Build image → Scan/kiểm thử → Push registry
→ Apply manifest → Rollout → Verify → Observe
→ Scale/update → Rollback khi cần → Retire
```

Application team quản lý Deployment, Service, Route, ConfigMap, Secret, PVC và policy trong project. Platform team quản lý cluster, node, Operator, ingress, storage, update và policy toàn cục. Ranh giới cụ thể phụ thuộc RBAC của tổ chức.

## 2. Chọn cách triển khai cluster

| Cách | Khi dùng | Đặc điểm |
| --- | --- | --- |
| Assisted Installer | Bare metal/vSphere/Nutanix hoặc môi trường được hỗ trợ, cần UI và preflight check | Dễ bắt đầu, installer hướng dẫn và kiểm tra host |
| Installer-provisioned infrastructure (IPI) | Hạ tầng được installer hỗ trợ và có quyền tạo tài nguyên | Installer tạo phần lớn hạ tầng và cluster |
| User-provisioned infrastructure (UPI) | Cần tự quản lý hạ tầng chi tiết | Người vận hành chuẩn bị LB, DNS, VM/network theo tài liệu |
| Agent-based Installer | Disconnected/restricted network hoặc cần workflow local | Sinh ISO agent và cấu hình khai báo tại chỗ |
| OpenShift Local | Máy cá nhân để học và phát triển | Cluster một máy, không đại diện đầy đủ production HA |
| Developer Sandbox | Học application workflow không cần tự dựng cluster | Không có quyền node/cluster-admin và có quota/thời hạn |

Luôn chọn tài liệu cài đặt đúng **release và platform**. Không tái sử dụng `install-config.yaml`, pull secret hoặc ignition file công khai; các file này có thể chứa thông tin nhạy cảm.

## 3. Kiểm tra trước khi triển khai ứng dụng

```bash
oc login --token=<TOKEN> --server=<API_URL>
oc whoami
oc whoami --show-server
oc project
oc get resourcequota,limitrange
oc auth can-i create deployments.apps
oc auth can-i create routes.route.openshift.io
```

Trước production deployment cần xác nhận:

- namespace/project và context đúng;
- quota còn đủ;
- image pull credential hoạt động;
- StorageClass và access mode phù hợp nếu có PVC;
- DNS/Route hostname và TLS strategy;
- request/limit, probes và replica count;
- RBAC/SCC/NetworkPolicy;
- cách rollback và nơi xem metrics/log.

## 4. Cấu trúc manifest đề xuất

```text
openshift-app/
├── base/
│   ├── deployment.yaml
│   ├── service.yaml
│   ├── route.yaml
│   ├── configmap.yaml
│   └── kustomization.yaml
└── overlays/
    ├── dev/
    └── prod/
```

Manifest nên đặt trong Git và render được bằng Kustomize hoặc công cụ GitOps. Secret thật không đưa vào Git; dùng secret manager/sealed workflow theo hệ thống của tổ chức.

## 5. Deployment, Service và Route

Manifest tối thiểu có khả năng vận hành tốt:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 2
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  selector:
    matchLabels:
      app: web
  template:
    metadata:
      labels:
        app: web
    spec:
      containers:
      - name: web
        image: quay.io/openshift/origin-hello-openshift:latest
        ports:
        - name: http
          containerPort: 8080
        readinessProbe:
          httpGet:
            path: /
            port: http
          initialDelaySeconds: 2
          periodSeconds: 5
        livenessProbe:
          httpGet:
            path: /
            port: http
          initialDelaySeconds: 10
          periodSeconds: 10
        resources:
          requests:
            cpu: 50m
            memory: 64Mi
          limits:
            cpu: 250m
            memory: 256Mi
        securityContext:
          allowPrivilegeEscalation: false
          capabilities:
            drop: [ALL]
          seccompProfile:
            type: RuntimeDefault
---
apiVersion: v1
kind: Service
metadata:
  name: web
spec:
  selector:
    app: web
  ports:
  - name: http
    port: 8080
    targetPort: http
---
apiVersion: route.openshift.io/v1
kind: Route
metadata:
  name: web
spec:
  to:
    kind: Service
    name: web
  port:
    targetPort: http
```

Không pin `runAsUser` nếu image hỗ trợ UID tùy ý; SCC thường cấp UID từ range của project. Với production, dùng image tag bất biến hoặc digest thay vì `latest`.

## 6. Quy trình triển khai và xác minh

```bash
oc apply -f manifests/
oc rollout status deployment/web --timeout=180s
oc get deployment,replicaset,pod,service,route
oc get endpointslice -l kubernetes.io/service-name=web
oc describe deployment/web
oc logs deployment/web --tail=100
oc get route web -o jsonpath='{.spec.host}{"\n"}'
```

Kiểm tra theo chuỗi:

1. Deployment có `Available=True`.
2. Pod có `Ready=True` và không restart bất thường.
3. Service selector khớp Pod labels.
4. EndpointSlice chứa địa chỉ Pod Ready.
5. Route được admission nhận và hostname phân giải được.
6. Request từ ngoài trả đúng status/content.

`oc apply` thành công chỉ chứng minh API chấp nhận object, chưa chứng minh ứng dụng phục vụ được traffic.

## 7. Cập nhật, rollback và scale

```bash
oc set image deployment/web web=<REGISTRY>/<REPOSITORY>@sha256:<DIGEST>
oc rollout status deployment/web
oc rollout history deployment/web
oc rollout undo deployment/web
oc scale deployment/web --replicas=3
oc get pods -l app=web -w
```

Rollback Deployment chỉ quay lại Pod template của revision; nó không tự rollback database schema, external service hay dữ liệu. Release có migration cần chiến lược tương thích ngược và backup riêng.

HPA cần metrics pipeline và resource request:

```bash
oc autoscale deployment/web --min=2 --max=6 --cpu-percent=70
oc get hpa
```

## 8. ConfigMap, Secret và rollout

```bash
oc create configmap web-config --from-literal=APP_MODE=production --dry-run=client -o yaml | oc apply -f -
oc create secret generic web-secret --from-literal=API_KEY='gia-tri-lab' --dry-run=client -o yaml | oc apply -f -
```

Nếu biến môi trường lấy từ ConfigMap/Secret thay đổi, container đang chạy không tự nhận giá trị mới. Cần rollout Pod, chẳng hạn:

```bash
oc rollout restart deployment/web
oc rollout status deployment/web
```

Không đưa Secret thật vào command history hoặc Git trong hệ thống thực; ví dụ trên chỉ dùng dữ liệu lab.

## 9. Vận hành thường ngày

### 9.1 Quan sát ứng dụng

```bash
oc get events --sort-by=.lastTimestamp
oc logs deployment/web --all-containers --tail=200
oc logs <POD> --previous
oc describe pod <POD>
oc adm top pods
```

`oc adm top` phụ thuộc metrics và có thể không được cấp quyền.

### 9.2 Quan sát nền tảng dành cho cluster administrator

```bash
oc get clusterversion
oc get clusteroperators
oc get machineconfigpools
oc get nodes
oc get csr
```

Không bắt đầu update cluster khi Operator đang Degraded, MachineConfigPool chưa ổn định hoặc chưa đọc release notes. Cập nhật cluster qua cơ chế được CVO hỗ trợ, không nâng thủ công từng gói trên RHCOS.

### 9.3 Debug theo tầng

| Triệu chứng | Kiểm tra đầu tiên |
| --- | --- |
| `Pending` | Events, quota, request, PVC, affinity/taint |
| `ImagePullBackOff` | image reference, pull secret, registry trust/network |
| `CrashLoopBackOff` | current/previous logs, command, config, probes |
| `CreateContainerConfigError` | Secret/ConfigMap/volume reference |
| SCC từ chối | error admission, SA và securityContext |
| Route 503 | Service selector, EndpointSlice, readiness, targetPort |
| Node NotReady | kubelet/CRI-O/network; cần quyền platform team |

## 10. Checklist production

- [ ] Image dùng digest hoặc tag bất biến và đã scan.
- [ ] Container chạy non-root/UID tùy ý, drop capabilities.
- [ ] Có request, limit và probes phù hợp.
- [ ] Có ít nhất hai replica khi ứng dụng cần HA.
- [ ] Có PDB và topology spread nếu yêu cầu khả dụng.
- [ ] Route TLS và certificate được kiểm tra.
- [ ] NetworkPolicy/RBAC/ServiceAccount theo least privilege.
- [ ] PVC, backup và restore đã được thử.
- [ ] Dashboard/alert/log và runbook đã tồn tại.
- [ ] Rollback ứng dụng và migration dữ liệu đã được diễn tập.
